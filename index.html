// how it works

What makes HanaLima possibleHanaLima だからできること、その理由

No magic and no kernel extensions: a handful of macOS APIs used in a way most tools don't, plus some careful plumbing around Lima's public interfaces. 魔法もカーネル拡張もありません。多くのツールが使っていない macOS の API の使い方と、Lima の公開インターフェースまわりの丁寧な配管だけです。

01

macOS 26 vmnet_network + one entitlement = rootless NAT with your subnetmacOS 26 の vmnet_network と entitlement 1 つで、root なしの NAT

The new vmnet API lets a process create a NAT or host-only network with a subnet you choose and DHCP reservations — as an ordinary user, as long as the binary is signed with com.apple.security.virtualization. (In the figures, uid 501 is the Mac's first ordinary user account; root is uid 0.)新しい vmnet API なら、サブネットを指定した NAT やホストオンリーのネットワークを、DHCP 予約付きで一般ユーザーのまま作れます。条件は、バイナリが com.apple.security.virtualization 付きで署名されていること。（図の uid 501 は、Mac で最初に作られる一般ユーザーの ID です。root は uid 0。）

02

Bridging to the LAN — also without rootLAN へのブリッジも root なし

The classic bridged mode is what socket_vmnet runs as root. We found that, with the same entitlement, vmnet_start_interface in VMNET_BRIDGED_MODE starts fine as uid 501. One interface per VM; two VMs plus en0 share bridge100, and the Mac keeps its IPv4. Works over Wi-Fi too: bridged to en1, a VM got its address from the LAN's DHCP and reached the router through the access point.従来のブリッジモードは、socket_vmnet が root で動かしているものです。同じ entitlement があれば、VMNET_BRIDGED_MODE の vmnet_start_interface が uid 501 のまま起動することを確かめました。VM ごとにインターフェースを作り、2 台の VM と en0 が bridge100 を共有しても、Mac の IPv4 は維持されます。Wi-Fi でも動きます。en1 にブリッジした VM が LAN の DHCP からアドレスを取得し、アクセスポイント経由でルーターまで届きました。

03

Speaking socket_vmnet's protocol, so Lima needs no patchessocket_vmnet のプロトコルを話すので、Lima は無改造

Lima already knows how to plug a VM into a UNIX socket: networks: - socket: PATH. The protocol is QEMU's stream format — a 4-byte big-endian length, then the frame. hanalima-netd speaks it on one side and vmnet on the other. Works for VZ and QEMU VMs.Lima はもともと、VM を UNIX ソケットにつなげます（networks: - socket: PATH）。中身は QEMU の stream 形式で、4 バイトのビッグエンディアンの長さに続けてフレームを送るだけ。hanalima-netd は片側でこれを話し、反対側で vmnet を話します。VZ でも QEMU でも動きます。

04

launchd socket activation: networks outlive the applaunchd のソケットアクティベーションで、アプリを終了しても動き続ける

Each network is a per-user LaunchAgent whose socket launchd owns. The helper starts on the first VM connection and exits when idle. Quit HanaLima, run limactl start from a shell — the network is still there.ネットワークごとにユーザーの LaunchAgent を登録し、ソケットは launchd が持ちます。最初の VM 接続でヘルパーが起動し、使われなくなると終了します。HanaLima を終了して、シェルから limactl start しても、ネットワークはそのまま使えます。

05

Fixed IPs that actually stick: DHCP option 61 surgery固定 IP を本当に効かせる、DHCP オプション 61 の手術

vmnet reserves addresses by MAC, but macOS's bootpd identifies a client by its client identifier when one is present — and Linux guests send a DUID. So the reservation never matched. The helper strips option 61 from DHCP requests, only for MACs that have a reservation. With no client identifier, bootpd falls back to the MAC address, the reservation matches, and the VM gets its fixed IP.vmnet の予約は MAC で行いますが、macOS の bootpd はクライアント識別子があればそちらで識別し、Linux のゲストは DUID を送ってきます。そのため予約が一致しませんでした。ヘルパーは、予約のある MAC からの DHCP 要求に限って、オプション 61 を取り除きます。識別子がなくなると bootpd は MAC アドレスで相手を識別するので、予約が一致し、VM に固定 IP が割り当てられます。

06

limactl is the API — and edits stay minimallimactl を API として使い、変更は最小限に

No Go code is linked; HanaLima reads limactl list --format json and the watch --json event stream. Form edits become limactl edit --set expressions for just the fields you touched, so Lima's defaults and your unknown keys survive, and Lima validates every change.Go のコードはリンクせず、limactl list --format json と watch --json のイベントを読みます。フォームの変更は、触った項目だけの limactl edit --set 式になるので、Lima の既定値や未知のキーは残り、変更はすべて Lima が検証します。

07

A VM's disk on an external drive — and back, anytimeVM のディスクを外付けドライブへ、いつでも行き来

Lima has no per-VM location, and it lists only real folders in ~/.lima: link a whole VM folder to another drive and the VM vanishes. So the folder stays and only disk, the one large file, moves out as a link Lima follows for start, resize and snapshots. The copy goes through copyfile with COPYFILE_DATA_SPARSE, which copies only the data extents, so the disk keeps its sparse size. The swap to the link is a single rename, so a failed or cancelled move leaves the original untouched.Lima には VM ごとの置き場所の設定がなく、一覧には ~/.lima の中の本物のフォルダしか出ません。VM のフォルダごと別のドライブへリンクすると、VM が消えてしまいます。そこでフォルダは残し、いちばん大きな disk だけをリンクで外へ出します。起動、拡張、スナップショットも Lima がリンクをたどってくれます。コピーは copyfile の COPYFILE_DATA_SPARSE で、データのある範囲だけを写すので、ディスクはスパースのままです。リンクへの置き換えは rename 1 回なので、失敗しても中止しても元のディスクは無傷です。

08

Snapshots for VZ VMs, made of APFS clonesVZ の VM にもスナップショットを、APFS のクローンで

Lima 2.2's VZ driver has no snapshots. HanaLima makes its own: with the VM stopped, it clones disk and the EFI variable store with APFS clonefile. A clone shares every block with the disk until either one changes, so it takes a moment and costs only what you write afterwards. Restoring clones it back with a single rename; the VM keeps its name, MAC addresses and fixed IPs. Clones work only within a volume, so snapshots sit on the disk's own volume. On VMs using HanaLima's driver, limactl snapshot itself works too and makes the same APFS-clone snapshots.Lima 2.2 の VZ ドライバーにはスナップショットがありません。そこで HanaLima が自前で用意します。停止中に disk と EFI の変数ストアを APFS の clonefile で複製します。クローンは、どちらかが書き換わるまで中身をすべて共有するので、一瞬で終わり、容量はその後に書いた分だけです。戻すときはクローンを作り直して rename 1 回。VM の名前、MAC アドレス、固定 IP はそのままです。クローンは同じボリューム内でしか作れないので、スナップショットはディスクと同じボリュームに置きます。HanaLima のドライバーの VM では limactl snapshot もそのまま動き、同じ APFS クローンのスナップショットを作ります。

09

Copies that are really separate — and know where they came from本当に独立したコピーを、コピー元の記録つきで

limactl clone copies a VM in a moment with APFS clones and gives it a new host name, MAC addresses and SSH keys. But it copies what it finds: the link to a disk on an external drive, so both VMs would write one disk; MAC addresses set by hand; the original's logs. HanaLima clones the moved disk on its drive, drops those MACs, empties the logs, and writes the parent's id into the copy's record. The Overview shows where each VM came from and its copies — even for copies and renames made with limactl itself.limactl clone は APFS のクローンで VM を一瞬で写し、ホスト名、MAC アドレス、SSH の鍵を新しくします。ただし、見つけたものはそのまま写します。外付けドライブにあるディスクへのリンク（2 台が 1 つのディスクに書き込むことに）、手で指定した MAC アドレス、元の VM のログ。HanaLima は、移したディスクをそのドライブの上でクローンし、その MAC を消し、ログを空にし、親の ID をコピーの記録に書きます。概要には、どの VM からコピーしたか、どんなコピーがあるかを表示します。limactl で直接行った複製や名前の変更も見分けます。

10

Installer ISOs on a Lima VM — install into Lima's own diskインストーラーの ISO でも Lima の VM に、Lima のディスクへ直接インストール

Lima boots only cloud images: it sets up a VM through cloud-init and waits for SSH, so an interactive installer never finishes. But a Lima VM is just files in ~/.lima/<name>/, and Lima reuses a disk and vz-efi that already exist. So HanaLima asks Lima for a VM with a 1 MiB placeholder image, which gives a blank disk of the size you chose; then it boots the ISO itself on Virtualization.framework, sharing Lima's disk, EFI variable store and machine identifier, and you install as usual in a window. One fix-up line in the installed OS installs cloud-init and resets it; from then on limactl start configures the VM like any other — user, key, guest agent, shares, provisioning. Since v0.12 the ISO boots inside HanaLima's own driver, so the install keeps going if you quit the app; the VM it creates is a VZ (Lima) VM.Lima が起動できるのはクラウドイメージだけです。cloud-init で VM を整えて SSH を待つ仕組みなので、対話式のインストーラーは終わりません。ところが Lima の VM は ~/.lima/<名前>/ のただのファイルで、すでにある disk と vz-efi は Lima がそのまま使います。そこで HanaLima は 1 MiB のダミーのイメージで Lima に VM を作らせ（選んだ大きさの空のディスクができます）、Virtualization.framework で ISO を自分で起動します。Lima のディスク、EFI の変数ストア、機械の識別子を共有したまま、ウインドウの中でいつもどおりインストールします。インストールした OS で仕上げの 1 行を実行すると cloud-init が入って初期状態になり、以後は limactl start がほかの VM と同じように設定します。ユーザー、鍵、ゲストエージェント、共有、プロビジョニングまで。v0.12 からは ISO を HanaLima 自身のドライバーの中で起動するので、アプリを終了してもインストールは続きます。できるのは VZ（Lima）の VM です。

11

Rescue boot: the VM's own files, HanaLima's own screen救出起動: VM のファイルはそのまま、画面は HanaLima のもの

Everything Lima does to a VM goes through SSH to the guest's eth0 — the console, the stop, even the readiness check. Its VZ driver attaches the serial port as a write-only log file, so when sshd stops answering there is no way in. The installer window already taught HanaLima to run a Lima VM on Virtualization.framework; the rescue boot reuses that on the installed OS: the same disk, vz-efi, vz-identifier and cidata.iso, plus a screen and keyboard. One detail matters: Lima's cloud-init network config matches eth0 by MAC address, so HanaLima computes the same address Lima would (52:55:55 + three bytes of SHA-256 over the Mac's platform UUID and the instance folder), and the guest comes up with its network. Lima locks the user's password, so a provisioning example sets a getty on tty1 that logs the user in; add it before you need it. While the rescue runs, Lima refuses to start the VM — VZ holds the EFI store. Since v0.12 the rescue runs inside HanaLima's own driver with Lima's user-mode NIC, so name resolution works and the VM keeps running if you quit the app.Lima が VM にすることは、コンソールも停止も準備完了の判定も、すべてゲストの eth0 への SSH を通ります。VZ ドライバーはシリアルポートを書き込み専用のログファイルとして付けるので、sshd が応えなくなると入る手段がありません。インストールのウインドウで HanaLima はすでに Lima の VM を Virtualization.framework で動かせるようになっていました。救出起動はそれをインストール済みの OS に使います。同じ disk・vz-efi・vz-identifier・cidata.iso に、画面とキーボードを足すだけ。要は 1 つ、Lima の cloud-init のネットワーク設定は eth0 を MAC アドレスで引き当てるので、HanaLima は Lima と同じ値（52:55:55 ＋ Mac のプラットフォーム UUID とインスタンスのフォルダの SHA-256 の先頭 3 バイト）を計算して付け、ゲストはネットワークごと立ち上がります。Lima はユーザーのパスワードをロックするので、tty1 の getty にユーザーをログインさせるプロビジョニングの例を用意しました。必要になる前に入れておきます。救出起動中は VZ が EFI の変数ストアを掴むので、Lima は VM を起動できません。v0.12 からは救出起動も HanaLima 自身のドライバーの中で、Lima のユーザーモード NIC 付きで動くので、名前解決が通り、アプリを終了しても VM は動き続けます。

12

Being the VM driver: Lima's external-driver interface, in SwiftVM ドライバーになる: Lima の外部ドライバーの仕組みを Swift で

Lima 2 looks for lima-driver-<name> executables and talks to them over gRPC on a Unix socket: Configure, Create, Start, Stop, and a few more. HanaLima ships lima-driver-hanalima inside the app bundle, points limactl at it, and at startup also copies it into Lima's own driver directory (/opt/homebrew/lib/lima/ with Homebrew, no sudo), so the terminal's limactl runs these VMs too. A VM with vmType: hanalima is still a Lima VM — same images, cloud-init, SSH, port forwarding, limactl list — but the virtual machine itself runs on Virtualization.framework in HanaLima's driver process, with Lima's user-mode network attached by passing one end of a socket pair to limactl usernet. Three things followed from owning the VM. The serial port becomes a socket in both directions (Lima's VZ makes it a write-only log). The screen is a window the driver can hide and show again, because Lima's own window call turned out to be unusable from outside (it is given ten seconds, after which the host agent quits). And a small side channel next to Lima's lets HanaLima ask the driver for a screenshot or the window — things the Lima interface has no verb for. Moving a VM between Lima's vz and this driver is a single limactl edit: both use the same disk, EFI store and machine identifier, and the driver's Validate step refuses what it can't run yet, so the edit fails cleanly instead of the next boot. One more thing fell out of owning the VM: SSH over vsock. A guest with systemd 256 or later already has sshd listening on vsock port 22 (systemd-ssh-generator), so the driver proxies Lima's SSH port straight into the VM with no network in between — and then Lima's user-mode NIC, the one piece of the guest's network that Lima never let you remove, can be left out. That is the isolation profile: a VM whose only neighbours are the networks you attach, with SSH, the guest agent and port forwarding intact. Two details made it work: the NIC has to exist, unplugged, because cloud-init's network config names it by MAC and drops everything if it's missing; and the boot scripts that reach for apt have to be switched off before the guest tries. Alpine and older systemd have no sshd on vsock, so a boot script installs a socat relay after one boot with NIC 0 on, and the same path works there too. The driver is now the default for new VMs; Lima's vz and QEMU remain a choice.Lima 2 は lima-driver-<名前> という実行ファイルを探し、Unix ソケットの gRPC で Configure・Create・Start・Stop などを呼びます。HanaLima は lima-driver-hanalima をアプリに同梱して limactl に場所を教え、起動時には Lima 自身のドライバーの置き場所（Homebrew なら /opt/homebrew/lib/lima/、sudo なし）にも写すので、ターミナルの limactl からもこの VM を動かせます。vmType: hanalima の VM も Lima の VM のまま。イメージ、cloud-init、SSH、ポート転送、limactl list はそのままに、仮想マシン本体だけが HanaLima のドライバーのプロセスの Virtualization.framework で動き、Lima のユーザーモードネットワークには socketpair の片側を limactl usernet に渡してつなぎます。VM を自分で持つと 3 つのことが続きました。シリアルポートは双方向のソケットになる（Lima の VZ では書き込み専用のログ）。画面はドライバーが隠して出し直せるウインドウになる。Lima 自身のウインドウの呼び出しは外からは使えないとわかったため（10 秒の制限があり、過ぎると hostagent が終わる）。そして Lima の隣に小さな側道を置き、スクリーンショットやウインドウなど Lima のインターフェースに動詞のない頼みごとを HanaLima から伝えます。Lima の vz とこのドライバーの行き来は limactl edit 1 回。ディスク、EFI の変数ストア、マシン識別子は同じファイルで、ドライバーの Validate がまだ動かせないものを断るので、次の起動ではなく編集の時点できれいに失敗します。VM を持つとついてきたものがもう 1 つ、vsock 越しの SSH です。systemd 256 以降のゲストは最初から vsock のポート 22 で sshd が待っている（systemd-ssh-generator）ので、ドライバーは Lima の SSH ポートをネットワークを介さずに VM へ直結できます。すると、Lima がどうしても外させてくれなかったユーザーモードの NIC を、付けないことができる。それが隔離プロファイルです。隣人は自分で足したネットワークだけ、SSH・ゲストエージェント・ポート転送はそのまま。要点は 2 つ。NIC は「付けてつながない」こと（cloud-init のネットワーク設定が MAC で名指しするので、無いと設定ごと捨てられる）と、apt に手を伸ばす起動スクリプトをゲストが試す前に切っておくことでした。Alpine や古い systemd のゲストには vsock の sshd が無いので、NIC 0 付きで一度起動すると起動スクリプトが socat の中継を入れ、同じ経路が通ります。いまではこのドライバーが新しい VM の既定で、Lima の vz と QEMU も選べます。

13

A switch in userspace: guest-only networks without vmnetユーザー空間のスイッチ: vmnet を使わないゲスト専用ネットワーク

The helper already spoke socket_vmnet's protocol to every VM — a length-prefixed Ethernet frame each way — and forwarded the frames into a vmnet network. For a guest-only network it forwards them to each other instead: learn the source MAC of each frame, deliver known unicast to that VM's socket, flood broadcast and the unknown to everyone else. No vmnet means no bridge interface, no host address and none of vmnet's quirks (the 1001 retries, the bridge that steals en0's address). What vmnet also brought was DHCP, so the helper carries a small one: it reserves by MAC (no client-identifier surgery this time), answers ARP for the server address, and deliberately leaves out option 3 — no router. It does name itself as the DNS (option 6, with the search domain hanalima), but that DNS answers only the names on its own leases, lima-<name>, and refuses everything else: refused, not “no such name”, so a VM that also has Lima's user-mode NIC goes on to its other resolver for the internet. Each VM gets its own bounded outgoing queue and writer thread, so one guest that stops reading can't stall the switch for the rest. Leases land in the same text format macOS uses, so the app's address view didn't have to learn anything new.ヘルパーはもともと、各 VM と socket_vmnet のプロトコル（長さ付きの Ethernet フレーム）で話し、そのフレームを vmnet のネットワークへ流していました。ゲスト専用ネットワークでは、流す先を VM 同士にします。フレームの送信元 MAC を覚え、既知の宛先はその VM のソケットへ、ブロードキャストと未知は残り全員へ。vmnet を使わないので、ブリッジのインターフェースも Mac 側のアドレスも、vmnet の癖（1001 の再試行、en0 のアドレスを奪うブリッジ）もありません。vmnet が持ってきていたものがもう 1 つ、DHCP です。それもヘルパーが小さく持ちます。予約は MAC で引き（今度はクライアント識別子の手術は要らない）、サーバーのアドレスの ARP に答え、オプション 3 はわざと配らない。ルーターは無い。DNS（オプション 6、検索ドメイン hanalima）には自分を名乗るが、答えるのは自分のリースにある lima-<名前> だけで、ほかは REFUSED にする。「無い」ではなく「断る」なので、Lima のユーザーモード NIC もある VM は、インターネットの名前をもう一方のリゾルバで引ける。VM ごとに上限つきの送信キューと書き込みスレッドを持つので、読むのをやめた 1 台がスイッチ全体を止めることはありません。リースは macOS と同じ書式で書くので、アプリのアドレス表示に新しいことを教える必要はありませんでした。

v0.11

Guest-only networks — a segment the Mac is not onゲスト専用ネットワーク ── Mac が参加しないセグメント

Every vmnet network puts the Mac on the wire as the gateway. A guest-only network doesn't use vmnet at all: HanaLima's helper switches frames between the VMs itself, and its own DHCP hands out addresses with no router, so the segment leads nowhere; the helper is also the DNS, answering only the VMs' own names (lima-<name>, also with .hanalima) and refusing everything else — refused, not “no such name”, so a VM that also has Lima's user-mode NIC still resolves the internet through its other resolver. Combine it with the driver's isolation profile and a set of VMs can talk to each other and to nothing else — the setup for trying something you don't trust. Ordinary VZ VMs can join too; fixed IPs work by MAC.vmnet のネットワークは、どの種類でも Mac がゲートウェイとして同じ線に乗ります。ゲスト専用ネットワークは vmnet を使いません。HanaLima のヘルパーが VM のあいだでフレームを中継し、自前の DHCP はルーターを配らないので、このセグメントはどこにも通じていません。DNS はヘルパーが務め、VM の名前（lima-<名前>、.hanalima 付きも）だけに答え、ほかは断ります。「無い」ではなく「断る」ので、Lima のユーザーモード NIC もある VM は、インターネットの名前をもう一方のリゾルバで引けます。ドライバーの隔離プロファイルと組み合わせると、VM 同士は話せるがそれ以外とは話せない、信用しきれないものを試すための一式になります。普通の VZ の VM も参加でき、固定 IP は MAC で効きます。

No signed release yet — build from source. You need macOS 26+, Xcode 26+ with the Metal Toolchain, and Homebrew.署名済みのリリースはまだありません。ソースからビルドしてください。必要なものは macOS 26 以降、Metal Toolchain 入りの Xcode 26 以降、Homebrew です。

  1. Install LimaLima を入れる

    Plus the extra guest agents for non-native architectures.別アーキテクチャ用の追加ゲストエージェントも一緒に。

  2. Build the appアプリをビルド

    The script builds a release, signs the network helper with the virtualization entitlement, signs the app ad hoc for your Mac, installs it into /Applications and opens it. Run it again to update.スクリプトがリリースビルドを作り、ネットワークのヘルパーに仮想化の entitlement を付けて署名し、アプリをこの Mac 用に ad-hoc 署名して、/Applications に入れて起動します。更新するときも同じコマンドです。

  3. Create a VMVM を作る

    ＋ New VM in the sidebar → pick a template (e.g. Ubuntu 24.04 LTS) → Create. New VMs use HanaLima's driver by default. The first start downloads the image.サイドバーの ＋ 新規仮想マシン → テンプレート（例: Ubuntu 24.04 LTS）を選んで作成。新しい VM は既定で HanaLima のドライバーを使います。最初の起動でイメージをダウンロードします。

  4. Add a bridged networkブリッジのネットワークを追加

    Networks → ＋ → Bridge → en0. Then Add NIC in the VM's Settings tab. No password prompt.ネットワーク → ＋ → ブリッジ → en0。VM の設定タブの「NIC を追加」で選びます。パスワードは聞かれません。

Hana lima — handmadeHana lima ── 手作り

In Hawaiian, hana means to make and lima means hand — and also five. The icon is a plumeria, Hawaii's five-petaled lei flower (and hana sounds like 花, "flower", in Japanese). Each petal is a VM, with vents and a status LED, built by hand around a glowing network core with a >_ prompt. ハワイ語で hana は「作る」、lima は「手」、そして「5」。アイコンは、ハワイのレイに使われる 5 弁の花・プルメリアです（hana は日本語の「花」とも響きます）。花びらの一枚一枚が、通気口と LED を持つ VM。>_ の光るネットワークの芯のまわりに、手で組み上げていきます。
