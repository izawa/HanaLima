# 設計メモ

HanaLima の設計上の判断と、その理由をまとめる。経緯は [03](03-development-log.md)、ネットワーク調査は [02](02-networking-investigation.md) を参照。

## 構成

| ターゲット | 役割 |
|---|---|
| `LimaKit` | `limactl` CLI のラッパー（UI 非依存）。`ProcessRunner`、`LimaClient`（list/watch/create/start/edit/disk/autostart、ログストリーム）、`InstanceConfig`（lima.yaml の差分を `--set` 式に変換）、`DownloadMonitor`、`HostInterfaces`（ブリッジ先の一覧）、`DriverInstaller`（同梱のドライバーを `<prefix>/lib/lima/` に写す）、`DriverControl`（ドライバーの制御ソケット `hanalima-ctl.sock` の相手） |
| `NetworkKit` | HanaLima 仮想ネットワーク: `VirtualNetwork`/`networks.json`、`LaunchAgentManager`、`HelperInstaller`、`DHCPClientIDFilter`、`DHCPLeases`、`NetworkConflict` |
| `hanalima-netd` | ネットワークごとに 1 プロセス。Lima の `socket:` ネットワーク（socket_vmnet 互換の QEMU stream: 4 バイト長＋フレーム）を vmnet に中継する。root 不要（`com.apple.security.virtualization` が必須） |
| `HanaLima` | SwiftUI アプリ。`AppModel`（@Observable, @MainActor）、`AppModel+Networks` |
| `lima-driver-hanalima`（`Driver/`、別パッケージ） | Lima の外部 VM ドライバー（docs/09）。hostagent から gRPC（Unix ソケット）で呼ばれ、Virtualization.framework で VM を自分のプロセスに起動し、NIC 0 は `limactl usernet` の子プロセスに socketpair の片側を SCM_RIGHTS で渡してつなぐ。`vmType: hanalima` の VM で使われる。画面（自分のウインドウ）、シリアルコンソール（`serialv.sock`）、HanaLima からの制御（`hanalima-ctl.sock`、`DriverControl`）も持つ。`build-app.sh` が virtualization の entitlement で署名して `Contents/Helpers/` に入れ（`LIMA_DRIVERS_PATH`）、アプリの起動時に `DriverInstaller` が `<prefix>/lib/lima/`（Homebrew なら `/opt/homebrew/lib/lima/`）にも写すのでターミナルの `limactl` からも使える。新規作成の既定（2026-11-06）。hosted モード（`--hosted`、gRPC なし、制御ソケットと `hanalima-hosted.pid`）で救出起動と ISO インストールの VM も動かす |

実行時のファイル配置: `~/Library/Application Support/HanaLima/{networks.json, bin/hanalima-netd-<hash>, net/<名前>.sock}`、`~/Library/LaunchAgents/org.izawa.HanaLima.net.<名前>.plist`（launchd のソケットアクティベーション）、`~/Library/Logs/HanaLima/net-<名前>.log`。

## 設計方針

- **Lima の Go コードはリンクせず、`limactl` CLI を呼ぶ。** CLI が Lima の公式で安定したインターフェースだから。JSON 出力（`list --format json`、`watch --json`、`disk list --json`）を使う。
- **lima.yaml は `limactl edit --set` で変更する。** フォームで変えた項目だけを式にし、リストは生の lima.yaml（Yams）から読む。こうすると Lima が補った既定値が書き込まれず、未知のキーも残る。YAML 全体の置き換えは、`VISUAL` にコピー用スクリプトを指定して `limactl edit --tty=true --start=false` で行い、Lima の検証を通す。
- **子プロセスは `$TMPDIR/HanaLima` で実行する。** `limactl edit` は失敗時に `lima.REJECTED.yaml` をカレントディレクトリに書くため。PATH の先頭には `/opt/homebrew/bin` を足す（Finder から起動したアプリは PATH を引き継がない）。
- **起動状態は `limactl list` の Running だけで判断しない。** Running になってから SSH が使えるまで約 1 分かかる。`watch` の `running` イベントか `limactl start` の完了で「準備完了」とし、コンソールはそれまで待つ（すぐ失敗したら 10 回まで自動で再試行）。
- **ログイン時の自動起動は Lima の `limactl autostart` に任せる。** 登録の有無は `~/Library/LaunchAgents/io.lima-vm.autostart.<名前>.plist` があるかで判定する（Lima 自身の判定と同じ）。登録した VM の `limactl start`/`stop` は Lima が launchd 経由で行うので、アプリ側の分岐は不要。
- **メイン画面は単一の `Window`、メニューバーは `MenuBarExtra`。** メニューバーに表示している間は、ウィンドウを閉じてもアプリは終了しない。メニューバーから開く操作（コンソール、新規作成）は、モデルの `consoleRequest`/`createRequested` を通して画面に伝える。
- **テンプレートの一覧は Lima から取り、表示名とグループは名前から作る**（`TemplateCatalog`）。一覧は `limactl info` の `templates`（`--list-templates` と同じ名前に、ファイルの場所が付く）。`ubuntu-24.04` → 「Ubuntu 24.04 LTS」（LTS は偶数年の .04）のように名前から組み立てるので、Lima の更新で版が増えてもそのまま並ぶ。`ubuntu`・`ubuntu-lts`・`debian`・`default` など最新版を指すテンプレートは、YAML の `base: - template:_images/<名前>` をたどって今の版を表示する（`_images/ubuntu` のような版なしの画像は、中身が同じ `_images/ubuntu-26.04.yaml` を探す）。知らない名前は「その他」に元の名前で出る。
- **使用量の画面は、`LIMA_HOME`（`limactl info` の `limaHome`）とダウンロードのキャッシュ（`~/Library/Caches/lima`、macOS では場所を変えられない）を、ファイルの実際の使用量（`du` と同じ）で集計する。** VM のディスクはスパースなので、名目のサイズは使わない。キャッシュの 1 項目には、ダウンロードしたファイル（`data`）と VZ 用に変換した `imgconv/raw` が含まれる。「すべて削除」は `limactl prune`。「使われていないイメージを削除」は HanaLima が判定してキャッシュの項目を消す（`prune --keep-referred` はテンプレートが参照するものも残すので、ほぼ何も消えない）。判定は、どれかの VM の lima.yaml に URL があれば使用中、テンプレート（`_images/` を含む）にだけあれば未使用、どちらにもなければ Lima の部品（nerdctl など、起動のたびに cidata へ入れるもの）として残す。VM の作成・起動中はダウンロードと重なるので押せない。保存先の変更（`LIMA_HOME`）は、すべての `limactl` 呼び出しと自動起動の登録に関わるので、まだ扱わない。
- **`limactl watch` は app の終了時に止める**（`ProcessRunner.terminateBackgroundProcesses`）。強制終了で残ったものは次回起動時に片付ける。
- **ネットワークは 3 系統（HanaLima の仮想ネットワークは 4 種類）。**
  1. HanaLima 仮想ネットワーク（NAT／ホストオンリー: サブネット指定、DHCP 予約。ブリッジ: 接続先インターフェースを指定。**ゲスト専用**: vmnet を使わず netd 自身が VM のあいだでフレームを中継する L2 スイッチ。Mac にインターフェースは生えず、netd の DHCP（`GuestOnlyDHCP`、MAC で予約）は既定では経路を配らない。ネットワークに**ルーター**（`router`、そのネットワーク上で経路役をする VM のアドレス）を指定すると、オプション 3 でその VM を既定の経路として配り、DNS の 2 番目にも並べ、そのアドレスはほかの VM に貸さない（隔離した VM 群をルーター VM 1 台の後ろに置く構成のため。`networks.json` には指定したときだけ書くので、古いヘルパーもそのまま読める）。DNS はオプション 6 で netd 自身（サーバーのアドレス）を配り、検索ドメイン `hanalima`（オプション 15）を付ける。netd の DNS はリースにある名前（VM が送ったホスト名、Lima では `lima-<名前>`。そのままか `.hanalima` 付き）だけに A で答え、ほかは REFUSED（リゾルバが次のサーバーへ進む。NXDOMAIN だと止まる）にするので、usernet もある VM はインターネットの名前を usernet 側で引ける。Ubuntu（systemd-resolved）は lima0 のリンク別 DNS と検索ドメインで `lima-<名前>` を引く。Lima の Alpine は usernet があると cloud-init の resolv.conf（usernet の DNS だけ）のままで、隔離（usernet なし）だと dhcpcd の resolv.conf が残り netd の DNS を使う。`gateway` は DHCP サーバーのアドレスで、ARP には答えるが ICMP には答えない。VM ごとに上限つきの送信キュー＋書き込みスレッドを持ち、読まない VM があっても他を止めない。リースは `net/<名前>.leases`（dhcpd_leases 形式）に書き、アプリは macOS のリースと合わせて読む。VM を丸ごと切り離すのは別の話（ドライバーの隔離プロファイル）で、ゲスト専用はその「隣人」を作る）: root 不要。
  2. vzNAT: root 不要。サブネットは指定できない。
  3. socket_vmnet（`lima:shared/host/bridged`）: Lima の従来方式。既存の VM のために表示・起動・編集はできるが、導入（root、sudoers）は HanaLima では行わず Lima の手順に任せる（2026-10-12 ユーザー判断）。未導入のときは NIC の追加メニューと組み込みの一覧に出さない。HanaLima のネットワークに機能面の不足はなく、socket_vmnet に残る利点は Lima 標準との互換（HanaLima なしでも動く `lima.yaml`）だけだったため。
- **HanaLima のブリッジは、VM の接続ごとに従来 API のインターフェース（`vmnet_start_interface` + `VMNET_BRIDGED_MODE`）を作る。** entitlement 付きの署名なら root なしで動く（macOS 27.0.1 で確認）。2 台同時、仮想ネットワークとの同時使用、再起動の順序も実機で確認済み（docs/02）。`vmnet_network` を使わないので、同時使用の確認ダイアログの対象外。
- **hanalima-netd の vmnet ネットワークは、最初の VM 接続時に作り、最後の VM が切断したら解放する。** 使い回すと、macOS の不具合で DHCP 予約が消え、ブリッジ番号も衝突する（下記）。
- **すべての終了経路でインターフェースを止めてから終了する。** 止めずに終了すると、vmnet がそのサブネットを再起動まで予約したままになる。シグナルハンドラは `@Sendable` にすること（main.swift のトップレベルに書いたクロージャは main actor 扱いになり、別スレッドで動くと SIGTRAP で落ちる）。
- **ヘルパーは上書きせず、バージョンごとに別名で置く（`bin/hanalima-netd-<hash>`、`bin/current`）。** launchd は登録時のプログラムの cdhash を記録していて、別のビルドで上書きすると次の起動が `spawn failed`（終了コード 78）になる。エージェントの登録し直しは、ヘルパーが動いていないときだけ行う（`upgradeIdleAgents`）。**netd は `networks.json` から自分の項目だけを読む**（`NetworkStore.network(named:)`: 生の JSON から名前で選んでその 1 つだけ decode）ので、新しいアプリが書いた知らない種類の項目があっても、その種類のヘルパー以外は起動できる。古い版のヘルパーが VM をつないだまま動いている間は入れ替えられないので、ネットワークを保存・削除したとき、登録先が現在のヘルパーでなく動いているエージェント（`staleHelpers`）の VM に「再起動が必要」の印を付け、帯で「ヘルパーが古い版のまま」と知らせる。アプリが居ないときに launchd が古い版を起動して失敗した分は、アプリを開けば `failed` も「動いていない」として付け替わる。
- **netd どうしは、vmnet の操作（ネットワークの作成、インターフェースの開始）をファイルロック（`net/vmnet.lock`）で 1 つずつ行う。** ネットワークの作成とブリッジの開始が重なると、そのプロセスでは 1001 が続く（新しいプロセスにすると作成できた）。
- **DHCP 予約は、予約のある MAC からの DHCP 要求に限り、オプション 61 を除去して効かせる。** bootpd はクライアント識別子（Linux の DUID）があるとそれで識別するため、MAC による予約が一致しない。
- **ネットワークを変えたあとの案内。** 実行中の VM が使うネットワークを保存・削除したら、その VM に「再起動が必要」の印を付け（`restartNeeded`）、VM の画面の帯とサイドバーで知らせる。印は再起動か停止で消える。削除したネットワークを指す NIC（`net/` の下のソケットで、`networks.json` に無いもの）は「削除したネットワーク」と表示し、起動・再起動の前に「NIC を外して起動」するか尋ねる。外すのは `limactl edit --set '.networks |= map(select(.socket != "…"))'`（実行中なら先に停止）。
- **VM のディスクを外付けドライブなどへ移せる（`ExternalDisk`）。** Lima は VM の置き場所を選べず、VM のフォルダごとシンボリックリンクにすると `limactl list` に出ない（docs/05）。そこでフォルダは `~/.lima` に残し、`disk` だけを `<選んだ場所>/HanaLima Disks/<名前>/disk` に移してリンクを置く。コピーは `copyfile` の `COPYFILE_DATA_SPARSE`（データのある範囲だけを写す）で `disk.partial` に取り、末尾の穴の分だけ長さを元に合わせ（copyfile は最後のデータで止まる）、サイズを照合してから改名し、最後に rename 1 回でファイルをリンクに置き換える（途中で失敗・中止しても元のディスクは残る）。戻すときも同じ手順で逆向き。移動先の判定（同じボリューム、APFS 以外、空き不足、既存のフォルダ）はシートで先に示し、通らなければ移動できない。外付けの空き容量は「重要な用途」の値が返らないことがあるので、通常の空き容量で補う。ドライブが外れているときは起動を止めて知らせ、VM の削除では移動先のフォルダ（目印の `hanalima.json` があるものだけ）も削除する。作成画面でも保存場所を選べる（作成後、最初の起動の前に移す）。選んだフォルダ自体が `HanaLima Disks` に似た名前なら、中にもう 1 段作らない。最後の VM を片付けて空になった `HanaLima Disks` も消す。ディスクの場所はモデルの状態として持ち、一覧の更新とボリュームのマウント・取り外しの通知で更新する（描画のたびにファイルを読むと、抜き差しで表示が古いまま残る）。`rsync --sparse` は使わない（ブロックごとにゼロか判定するので、散らばったデータで約 2 倍に膨らむ）。**`limactl clone` はリンクをそのまま写す**ので、コピーした VM は元の VM と同じディスクを指す。目印の `instanceDir` が持ち主で、削除で消すのは持ち主のディスクだけ。持ち主でない VM は「ディスクを共有」と表示して起動を止め、「ディスクを独立させる」で同じドライブの上に APFS のクローン（`clonefile`）を作ってリンクを付け替える。目印の VM がもう無いかリンクしていない（Lima の外で改名・削除された）ときは、いまリンクしている VM が目印を引き継ぐ。
- **作成画面で、ホームフォルダの共有を外せる。** Lima のテンプレートは `_default/mounts` でホーム（`~`、読み取り専用）をマウントするので、VM から Mac の認証情報（`~/.ssh` など）を読める。AI のエージェントなどを隔離して動かす用途のために、切り替えをオフにすると `limactl create --mount-none` を付ける（テンプレートのマウントはすべて外れる）。既定はオンで、Lima と同じ。オフのときは作業フォルダを 1 つ選べ、`--mount-only=<パス>[:w]` でそのフォルダだけを（VM の中でも同じパスに）共有する。パスに `:` を含むフォルダは選べない（Lima が `:w` の区切りとして読む）。共有を外して隠せるのはファイルだけで、NIC 0 を付けたままなら、それを通って Mac の `127.0.0.1` のサービス、LAN、インターネットに届く。そこで、隔離しないときは作成画面に注意を出す（docs/06）。NIC 0 を外せるのは HanaLima のドライバーの隔離プロファイルだけで、Lima の vz と QEMU には外す設定がない。
- **VM の複製（`InstanceCopy`）は `limactl clone` に任せ、残りを HanaLima が補う。** clone は APFS のクローンで一瞬に写し（10 GB・実使用 267 MB で 25 ミリ秒）、ホスト名、MAC、VZ のマシン識別子、SSH のポートとホスト鍵を新しくする。HanaLima は、手で指定した MAC を消し（`--set 'del(.networks[].macAddress)'`）、写ったログを空にし、外付けのディスク（リンクが写る）を同じドライブの上でクローンし、記録を書く。複製は停止中だけ。固定 IP（MAC に結びつく）と自動起動は引き継がない。複製元と複製の DHCP: ゲストの DUID はディスク上のファイルなので複製でも同じだが、HanaLima のネットワーク（bootpd）では別の IP になる（E2E、Alpine・Fedora・Ubuntu LTS）。Alpine の dhcpcd は識別子を IAID（既定は MAC から作る）＋DUID にし、Ubuntu は Lima の netplan で MAC を識別子にするため。netd のオプション 61 の除去は、予約のある MAC に限ったままにする。
- **VM ごとの記録 `~/.lima/<名前>/hanalima-vm.json`（`InstanceMetadata`）。** ID、作成日時、テンプレート、親（ID、当時の名前、日時、スナップショット名）、メモ。VM のフォルダに置くので `limactl rename` で付いていき、`delete` で消える。親だけを持ち、子は持たない（コピーは独立していて、つながりは情報にすぎない。何世代でも 1 VM 1 ファイル）。clone は記録も写すので、記録のフォルダと今のフォルダが違えば、同じ ID の VM が元の場所にいれば CLI の複製（新しい ID、親はその VM）、いなければ名前の変更（ID を保つ）と判断して直す。サイドバーは平らなまま、系譜は概要タブに出す。
- **VZ のスナップショット（`DiskSnapshot`）は、ディスクと `vz-efi` の APFS クローン。** Lima 2.2 の VZ ドライバーにはスナップショットがない。クローンは同じボリューム内でしか作れないので、ディスクと同じボリュームに置く: 内蔵なら `~/.lima/_hanalima-snapshots/<VM の ID>/<ID>/`、外付けなら `HanaLima Disks/<名前>/snapshots/<ID>/`。**VM のフォルダの中には置かない**（サブフォルダがあると `limactl clone` が permission denied で失敗した）。`_` で始まるフォルダは Lima が VM として数えない。戻すときはクローンを `disk.hanalima-restoring` に作って rename で置き換え、保存後に広げたディスクは長さを保つ。戻したら VM のフォルダの `ssh.known_hosts` を消す。Lima 2.3 は最初の起動でゲストの SSH のホスト鍵をこのファイルに記録し、以後は違う鍵を断る。2.2 の頃のスナップショットには鍵を保つ cloud-init の設定が無く、戻すと次の起動で鍵が作り直されるため。消しておけば、次の起動で鍵を記録し直す。停止中だけ。スナップショットがあるあいだはディスクを移動できない（同じボリュームに置くため）。HanaLima で VM を削除すると消す（CLI で削除すると残る）。UI は「VM が増えるのが複製、同じ VM の過去に戻るのがスナップショット」で分け、スナップショットから新しい VM も作れる（複製してからスナップショットを戻す）。
- **持ち主のいないデータ（`Leftovers`）を使用量に出す。** HanaLima のスナップショットと外付けのディスクは Lima が知らないので、`limactl delete` で VM を消すと残る。`_hanalima-snapshots/<ID>` はどの VM の記録の ID でもないもの、外付けの `HanaLima Disks/<名前>` は目印の VM のフォルダがもう無く、どの VM のリンクも指していないものだけを残りものとする（目印のないフォルダ、Lima の外で改名した VM、移動中のディスクは対象外）。外付けは、HanaLima がディスクを置いたフォルダを覚えておき（UserDefaults `knownExternalDiskFolders`。一覧の更新のたびに外付けの VM から覚える）、接続中のものだけ調べる。削除の直前にもう一度判定する。スナップショットの容量は持ち主の VM の行に数える。
- **プロビジョニングの例（`ProvisionExamples`）を同梱する。** 基本ツール一式、dotfiles・公開鍵、Docker Engine、XDP の開発環境、日本向けの設定（タイムゾーンとロケール）、自動更新の停止、スワップファイル、開発言語（Go・Node.js・uv・rustup）、パッケージをすべて更新（一度だけ。`ProvisionOnce` の例で、追加・実行のたびに新しい印の id を付ける）、コンソールに自動ログイン、出口を絞るゲートウェイ（ゲスト専用ネットワークの「ルーター」に指定する VM 用。nftables と dnsmasq で、後ろの VM に NAT と DNS を与え、`/etc/hanalima/gateway.conf` の許可リストの先だけ通す。ホスト名は dnsmasq の nftset で、後ろの VM が引いたときに集合へ入る。落としたパケットは `hanalima-gateway` の前置きでログ。E2E は `GatewayEndToEndTests`: Alpine のゲートウェイとクライアントを vz で起動し、クライアントの usernet の経路を消して、許可した先だけ届くこと、`*` を足して再実行すると全部届くことを確かめる）。設定タブの「例から追加…」で選ぶと、普通の項目として追加され、そのまま編集できる。Lima は起動のたびにプロビジョニングを実行するので、どのスクリプトも「済んでいれば何もしない」形にし、apt・dnf・apk を見分ける。公開鍵は `authorized_keys` に追記する（Lima の鍵があるので上書きしない）。Docker のグループは、Lima が使い回す SSH の接続には次のログインまで反映されない。スクリプトは LimaKit に、名前と説明はアプリ側に置く（翻訳のため）。E2E（`ProvisionExamplesEndToEndTests`）で Ubuntu LTS・Fedora・Debian・Alpine を確認（2026-10-27 に足した 5 つは ubuntu-lts・alpine・fedora。Debian は未確認）。
- **プロビジョニングの「今すぐ実行」と「一度だけ実行」。** Lima のプロビジョニングは起動のたびに走るので、HanaLima が 2 つを足す。(1) 今すぐ実行（`ScriptRun`、`ProvisionScripts`）: 項目か例を、保存せずに実行中の VM で `limactl shell --tty=false <名前> sh -s`（標準入力にスクリプト）で実行し、出力をシートに流す。順番は起動時と同じ（data はファイルを書く、system は `sudo`、user はそのまま）。Lima のテンプレート変数（`{{.User}}` `{{.Home}}` `{{.UID}}` `{{.Name}}` `{{.Hostname}}`）はゲストの中で `sed` で展開する。data の親フォルダが無ければ所有者で作る（cloud-init は root のまま残す）。実行中は操作（`Operation.Kind.runScript`）として数え、起動・停止と重ならない。(2) 一度だけ実行（`ProvisionOnce`）: system・user のスクリプトを固定のラッパーで包み、成功したら印（root は `/var/lib/hanalima/once/<id>.done`、user は `$HOME/.local/state/hanalima/once/`）を残して以後の起動では何もしない。失敗は印を残さず次の起動で再試行する。本体はサブシェルで走らせるので、本体の `exit` でも印は付く。編集画面は本体だけを見せ、「もう一度実行」で id を変える。印はディスク上にあるので、複製は引き継ぎ、スナップショットを戻すとその時点に戻る。E2E は `ProvisionOnceEndToEndTests`（Alpine、2 回起動＋今すぐ実行）。
- **Ansible はホストから `ansible-playbook` を直接呼ぶ（`Ansible`、docs/08）。** Lima の `mode: ansible` は非推奨なので使わない。HanaLima が触るのは Ansible の安定した外側だけ: INI のインベントリ（`~/Library/Application Support/HanaLima/ansible/inventory.ini`。`[hanalima]` に全 VM、ホスト名 `lima-<名前>`、`ansible_ssh_common_args='-F <ssh.config>'`。Lima の `ssh.config` に鍵・ユーザー・ポート・ホスト鍵の検証（Lima 2.3 は `StrictHostKeyChecking yes` と VM ごとの `ssh.known_hosts`）・ControlPath が揃うので、これだけで届く。一覧が変わるたびに書き直す）、`ansible-playbook -i … --limit lima-<名前> <playbook>` の起動（作業ディレクトリは Playbook のフォルダ。`roles/`・`ansible.cfg` が効く）、終了コード。コールバックや Python API、collection には触れない。`ansible-playbook` は候補（`/opt/homebrew/bin`、`~/.pyenv/shims`、`~/.local/bin`、`/usr/local/bin`、PATH）を `--version` で実際に走らせて探す（Intel 版の残骸は「bad CPU type」で落ちる）。設定で場所を指定できる。VM ごとの記録（`hanalima-vm.json` の `ansible`）に Playbook のパス、追加引数、最終実行。出力は「今すぐ実行」のシート。「一度だけ」の印は付けない（冪等性は Playbook の流儀）。E2E は `AnsibleEndToEndTests`（Ubuntu LTS。Alpine には python3 が無い）。
- **インストーラーの ISO から VM を作る（`HostedProcess`（旧 `HostedVM`・`InstallerVM`）・`InstallSession`・`InstallerFixup`、docs/07）。** Lima は cloud-init 対応のイメージしか起動できないが、VM のファイルは `~/.lima/<名前>/` のただのファイルで、Lima は既存の `disk`・`vz-efi` をそのまま使う。そこで 1 MiB のダミーの raw イメージで `limactl create` して空の `disk` を作らせ、ドライバーの hosted モード（`lima-driver-hanalima --hosted`、アプリとは別のプロセス。2026-11-05 まではアプリ自身の VZ）で ISO を USB の記憶装置として EFI 起動し、Lima の `disk`・`vz-efi`（インストーラーが書く起動エントリが残る）・`vz-identifier` を共有して OS を入れる。画面はドライバーのウインドウで、クリップボードは届かない（VZ の制約）。アプリを終了しても VM は動き続け、次の起動で再接続する（救出起動の項）。インストール後、ラベル `HANALIMA` の小さな ISO（`limaify.sh`、Lima の公開鍵、ユーザー名）を使って `sudo mount -L HANALIMA /mnt && sudo sh /mnt/limaify.sh` を手入力してもらい、cloud-init と sshd を入れ、インストーラーが残した cloud-init の設定を消して `cloud-init clean` で「次が初回」にする。あとは `limactl start` で Lima の cidata が設定する。記録に `pendingInstall` を持ち、Lima の起動が成功するまで起動・複製・ディスクの移動を止め、画面に「インストーラーを開く」を出す（印は Lima の初回起動が成功した時点で消す）。containerd はオフ。VZ（Lima）専用、hanalima では作成しない（作成画面は ISO を選ぶと仮想化方式を vz に戻す）。ディスクはまず Mac の中。E2E は無人インストール（`InstallerAutoinstall`: ISO の shim と GRUB を FAT イメージに写し、HanaLima の `grub.cfg` で `autoinstall` を付けて EFI 起動。直接のカーネル起動は EFI が無くブートローダーの設定で失敗する。無人設定の YAML は `: ` を含む行を必ず引用する）。
- **HanaLima 自身の VM ドライバー（`Driver/`、`lima-driver-hanalima`、docs/09）。** Lima 2.x の外部ドライバーの仕組み（`lima-driver-<名前>` を hostagent が gRPC で呼ぶ）で、`vmType: hanalima` の VM を HanaLima が Virtualization.framework false` を埋める（cidata は `vmType == "vz"` 以外に QEMU 流の 192.168.5.3 を DNS にするため）。`build-app.sh` が virtualization の entitlement で署名して `Contents/Helpers/` に入れ、アプリは `LIMA_DRIVERS_PATH` でそこを指す。**ターミナルの が届かなかったときの取り残しも同じ規則で片付く）。残件（2026-11-06）: 一時停止（`pause`／`saveMachineState`）、macOS ゲスト、Alpine の追加ディスクの揺らぎ（Lima の mdev の競合。upstream に報告するかは未定）、vsock 探索の設計メモ、取り残されたドライバーの原因（番犬で回避済み）。検証済みのゲスト: Alpine・Ubuntu LTS・Fedora・Debian（2026-11-06、docs/09）。
- **一時停止（docs/11、段階 1）は、HanaLima のドライバーの VM だけ。** VZ の `pause()`／`resume()` で、ゲストの RAM はドライバーのプロセスに残る（用語は docs/11 の 0 章: RAM を持ったまま止めるのが一時停止、RAM の中身を Mac のファイルに書いてプロセスを終えるのが休止）。Lima のドライバーのインターフェースに一時停止は無いので、制御ソケットの `pause`・`resume` で行い、Lima の vz の VM には付けない（2026-11-08 ユーザー判断）。Lima は一時停止を知らず Running のままなので、アプリは実行中の hanalima の VM ごとに `status` を聞いて「一時停止中」を出す（アプリを終了しても一時停止は残り、次の起動で分かる）。ドライバーは、一時停止のときにゲストエージェントへの経路（`ga.sock`）の接続を切り、一時停止中に来た接続はすぐ閉じる。Lima のホストエージェントはゲストエージェントへの呼び出しに期限を付けておらず、止まったゲストへの呼び出しが返らないと `limactl stop` が終わらなくなるため。`GuestAgentConn` を断る形にすると Lima が約 2 秒ごとに Error のログを書くので、断らずに接続を閉じる（それでも gRPC のつなぎ直しの Info のログが 1 分に約 55 行残る）。60 秒以上止めたあとの再開では、NIC のリンクを 1 秒落として戻す（ゲストの時計は一時停止中に進まず、DHCP のクライアントがサーバーでは切れたリースを使い続けるため。リンクが戻るとリースを確かめ直す。Alpine は約 5 秒経路が消える）。アプリは `pausing`・`resuming` も一時停止中として扱い、`status` に答えが無ければ前の印を保つ。停止の要求（`limactl stop`、制御ソケットの `stop`）が来たら、先に再開してから ACPI の電源ボタンを送る（正常に止める。`forceStop` と `limactl stop -f` はそのまま）。SSH の準備（`AdditionalSetupForSSH`）が済むまでと、停止中は一時停止を断る。アプリでは、一時停止中はコンソール、今すぐ実行、Ansible を使えなくし、画面のサムネイルに「一時停止中」を重ねる。E2E は `DriverPauseEndToEndTests`（65 秒止めて再開し、リンクを落として戻したあともアドレスがあること、`boot_id` が同じで時計が合うこと、一時停止中の `limactl stop` が電源断でなく ACPI で終わること。Alpine と Ubuntu LTS で通過、停止は 3〜5 秒）。
- **救出起動（`RescueSession`・`HostedProcess`）: SSH で届かなくなった VM を、HanaLima のドライバーが画面付きで起動する。** Lima 2.2.1 の VZ ドライバーはシリアルポートを書き込み専用のログファイル（`serialv.log`）として付けるので、ゲストへ入力する経路がなく、sshd を壊した VM には入れない（docs/03 §31）。そこでインストーラーの仕組み（`HostedVM`、旧 `InstallerVM`）を流用し、停止中の VM の `disk`・`vz-efi`・`vz-identifier`・`cidata.iso` を Lima と同じように付け、画面・キーボード・NIC 1 つ（usernet、Lima の MAC。2026-11-05 までは VZ の NAT）で起動して、画面のコンソール（tty1）から直してもらう。NIC の MAC は Lima と同じ値（`LimaMACAddress`: `52:55:55` ＋ SHA-256(IOPlatformUUID ＋ インスタンスのフォルダ) の先頭 3 バイト）にする。Lima は cidata の network-config で eth0 を MAC で引き当てるので、違う MAC だと eth0 が上がらない。cidata を付けるのは cloud-init が同じインスタンスと見て何もしないため。付かないもの: 追加ディスク、共有フォルダ、HanaLima のネットワーク、ポート転送、ゲストエージェントの相手。名前解決は usernet の 192.168.5.2 で通る（VZ の NAT だった頃は netplan の固定と食い違って通らないことがあった）。Lima はユーザーのパスワードをロックする（`lock_passwd: true`）ので、プロビジョニングの例「コンソールに自動ログイン（画面・シリアル）」（tty1 と hvc0 に `agetty --autologin`。systemd はドロップイン、Alpine は agetty を入れて inittab）を入れた VM だけログインできる。実行中は操作（`Operation.Kind.rescue`）として数え、起動・複製・削除・ディスクの移動と重ならない。VZ の Linux ゲストのみ（macOS のゲストは `VZMacPlatformConfiguration` が要るので対象外）。**2026-11-05 の統合（残件 10）: 救出起動と ISO インストールは、アプリ本体の VZ（`HostedVM`）ではなく、ドライバーの hosted モード（`lima-driver-hanalima --hosted <dir> --cpus --memory [--iso] [--boot-image] [--helper] [--seed] [--no-cidata] [--headless] [--serial-log]`）で動く。** gRPC は立てず、制御ソケット（`hanalima-ctl.sock`: `status`・`openScreen`・`screenshot`・`stop`・`forceStop`）と pid ファイル `hanalima-hosted.pid`（`hanalima.pid` と分ける: Lima が hanalima の VM と誤認しないため）だけ。画面はドライバーのウインドウで、hosted ではウインドウを閉じると電源が切れる（Lima 配下では隠すだけ）。NIC 0 は VZ の NAT ではなく usernet（Lima の MAC）にしたので、cidata が eth0 の DNS を 192.168.5.2 に固定していても名前解決が通る。アプリ側は `HostedProcess` がドライバーを起動して制御ソケットを 1 秒おきに見るだけで、VM はアプリを終了しても動き続け、次の起動で `hanalima-hosted.pid` と制御ソケットから再接続する（`reattachHostedBoots`。`pendingInstall` があればインストール、無ければ救出のセッションに戻す）。アプリ本体の virtualization の entitlement は不要になったが、この回では残している。E2E は `RescueEndToEndTests`（ドライバーの hosted モードをヘッドレスで起動し、シリアルの `login:` か、usernet の `wait_port` で 22 番が開くのを待ってから制御ソケットで止め、Lima で再起動）。
- **socket_vmnet と HanaLima ネットワークの同時使用は、確認ダイアログを出したうえで許可する**（`NetworkConflict`）。netd はネットワークを使い回さないので、実機の 6 パターン（起動・再起動の順序、1 台の VM に両方の NIC）で問題は起きなかった。ほかのツールや古い netd が使い回すと macOS の不具合が起きうるので、警告は残している。

## v0.4 の機能と Lima 2.2.1 の実際の挙動

- **Lima のスナップショットは QEMU のみ、停止中だけ操作する**（VZ は HanaLima 独自の `DiskSnapshot`。上記）。Lima の VZ ドライバーは `unimplemented`。hanalima の VM では `limactl snapshot` がドライバーのスナップショット RPC を通って同じ `DiskSnapshot` を使う（停止中だけ、タグは 1 語。2026-11-05）。QEMU では、停止中は `qemu-img` の内部スナップショット（起動ディスクのみ）で、作成・適用・削除とも正しく動く。実行中は HMP `savevm` を使うが、9p の共有フォルダがあると QEMU が拒否し、**limactl は終了コード 0 を返す**（何も作られない）。さらに、`loadvm` に失敗すると VM が `restore-vm`（停止）のまま残る（QMP `cont` で再開できた）。そのため HanaLima は停止中だけ操作を許し、作成後は一覧にタグがあるかを確かめる。一覧は Lima 2.3 の `limactl snapshot list --json` を読み、このフラグを知らない 2.2 では qemu-img の表を読む。2.3 の表は ID・TAG・CREATED の 3 列で、メモリの状態の大きさが無いので、その列は「—」と出す。
- **スクリーンショットは、画面を有効にした VZ の VM だけ。** `limactl screenshot` は、ホストエージェントが表示している VM のウィンドウを `CGWindowListCreateImage` で撮る。QEMU は非対応、`video.display: none`（既定）では撮れない。ウィンドウを閉じると撮れなくなる。hanalima の VM では `limactl screenshot` が届かないので、制御ソケット `hanalima-ctl.sock` の `screenshot`（ドライバーが自分のウインドウを同じ `CGWindowListCreateImage` で写す）を使う（2026-11-05）。概要タブでは 3 秒ごとに更新する（表示中のみ）。
- **ログは差分だけ読む。** `ha.stderr.log`（logrus の JSON）と `serial*.log` を、前回の位置から追記分だけ読む（`LogFileFollower`）。Lima は起動のたびにファイルを作り直すので、i-node が変わるか小さくなったら最初から読み直す。シリアルの ANSI エスケープは除去する。
- **プロビジョニングは起動のたびに実行される**（cloud-init の `scripts_per_boot`）。冪等に書く必要があることを画面に明記している。スクリプト系（system/user/boot/dependency）と data は編集でき、`file` を使うものや yq・ansible は読み取り専用で保持する。
- **コードの編集は `CodeEditor`（NSTextView）で行う。** SwiftUI の TextEditor はシステム設定に従ってスマート引用符やダッシュに置き換えるため、スクリプトや YAML が壊れる。
- **メイン画面はメニューバーのアイコンから開く。** ウィンドウを閉じた状態で終了すると、ウィンドウの復元で「ウィンドウなし」が戻り、`.defaultLaunchBehavior(.presented)` や `.restorationBehavior(.disabled)` でも開かなかった。常に存在するメニューバーのラベルが、起動時にウィンドウがなければ `openWindow` で開き、`bootstrap()`（1 回だけ実行）も始める。

## 多言語対応

- **String Catalog（`Resources/Localizable.xcstrings`）を使い、元の言語は日本語。** キーは日本語の原文で、英訳をカタログに持つ。
- **文字列の抽出は Swift コンパイラーで行う**（`scripts/update-strings.sh`）。SwiftPM のビルドには Xcode のような自動抽出がない。`xcstringstool extract`（軽量な構文解析）は引数の型が分からず `%arg` を出すので、実行時のキー（`%@`、`%lld`）と一致しない。`-emit-localized-strings` でコンパイルすると正しいキーが得られる。別の scratch path でビルドするので、通常のビルドを壊さない。
- **`scripts/check-strings.py` で漏れを調べる。** コードで組み立てた文字列（`String(localized:)` が必要）、`LabeledContent(_:value:)` の value（翻訳されない）、文の一部だけを三項演算子で切り替えるもの（語順が言語で違うので文全体を書き分ける）が漏れやすい。
- **アプリの既定の言語は英語**（`CFBundleDevelopmentRegion = en`）。日本語でも英語でもない環境では英語になる。その代わり、日本語の訳がないキーは英語の表（複数形の規則も）を探しに行くので、`update-strings.sh` がすべてのキーに日本語の値を明示する。
- **「停止」のように、日本語では同じでも英語で訳し分けるものは、別のキーにする**（`vm-status.stopped`、`defaultValue: "停止"`）。
- **操作名に「中」を付けるような組み立てはしない。** 英語では語尾を付けられないので、`progressLabel`（「起動中」「Starting」）を別に持つ。

## macOS を更新したときの確認

HanaLima は、ドキュメントに約束されていない macOS の振る舞いに頼っているところがある。Apple は告知なく変えることがあるので、macOS のメジャー・マイナーの更新のたびに、次を確かめる（結果は docs/03 に記録する）。

| 頼っている振る舞い | 変わったときの影響 | 確かめ方 |
|---|---|---|
| `copyfile` の `COPYFILE_DATA_SPARSE` がデータの範囲だけを写し、末尾の穴で止まる | ディスクの移動で容量が膨らむ、またはディスクの長さが変わる | `swift test --filter ExternalDisk`（使用量が元と同じか、長さを補えているか、中止で何も残らないか） |
| シンボリックリンクにした `disk` を Lima（VZ・QEMU）がたどる。`limactl list` は本物のフォルダしか数えない | 外付けに移した VM が起動しない、または一覧から消える | `HANALIMA_E2E=1 swift test --filter ExternalDiskEndToEnd` |
| 外付けのボリュームの空き容量（「重要な用途」の値が返らないことがある） | 移動先が「空き不足」と誤判定される | 同上と、実機の外付けで移動のシートを開く |
| entitlement 付きの署名なら `vmnet_network` と従来のブリッジが root なしで動く | 仮想ネットワーク・ブリッジが作れない（1002 など） | `NetworkEndToEndTests`、`DHCPReservationEndToEndTests`、`BridgeEndToEndTests`（ブリッジはユーザーに確認してから） |
| vmnet の既知の不具合（下の節）とその回避 | 直っていれば回避が不要に、悪化していれば新しい回避が必要に | `Prototypes/vmnet-bridge100-repro`、上のネットワークの E2E |
| launchd が登録時のプログラムの cdhash を覚えている | ヘルパーの更新で `spawn failed`、または回避が不要に | アプリの更新後に `launchctl print gui/$(id -u)/org.izawa.HanaLima.net.<名前>` の終了コード |
| `NSWorkspace` のマウント・取り外しの通知 | ドライブの抜き差しで表示が古いまま残る | 外付けを抜き差しして、VM の画面の表示が切り替わるか |
| Lima の CLI（`limactl info`/`list`/`watch` の JSON、`prune`、`autostart`） | Lima の更新でも同じ。一覧・テンプレート・使用量が崩れる | 単体テストと `EndToEndTests` |
| `CGWindowListCreateImage`（非推奨。ドライバーが `dlsym` で呼び、自分のウインドウを写す） | 関数が消えると hanalima の VM のサムネイルと `screenshot` が撮れなくなる（ScreenCaptureKit は画面収録の許可が要る） | hanalima の VM で画面を開き、概要タブのサムネイルが出るか。`DriverEndToEndTests` |
| Lima の外部ドライバーの gRPC 定義（`pkg/driver/external/driver.proto`）。`Driver/driver.proto` はその写し | Lima の更新で RPC やメッセージが変わると、ドライバーの応答が読まれなくなる（2.3 ではスナップショットの一覧が空になった） | `git diff v<旧>..v<新> -- pkg/driver/external/driver.proto`。変わっていれば写し直して、`protoc` と依存パッケージからビルドした `protoc-gen-swift`・`protoc-gen-grpc-swift-2` で `Generated/` を作り直す。`DriverEndToEndTests` と `DriverSnapshotEndToEndTests` |
| Lima の `usrlocal.LibexecLima` が `<prefix>/lib/lima/` も探す（`DriverInstaller` の写し先。Lima の更新でも同じ） | ターミナルの `limactl` が `hanalima` を知らなくなる（`list` に「not a registered driver」） | アプリを起動したあと、ターミナルで `limactl info` の `vmTypes` に `hanalima` が出るか |

## macOS vmnet の既知の不具合（2026-10, macOS 27.0.1）

- アイドルになった `vmnet_network` は、ref を保持していても DHCP 予約とポート転送規則を失う（[フォーラム 847642](https://developer.apple.com/forums/thread/847642), FB24895271）。
- ブリッジ番号はネットワークの初回起動時に決まり、使い回すと衝突する（[apple/container#2051](https://github.com/apple/container/issues/2051)）。インターフェースを止めた `vmnet_network` を再利用すると、従来 API のブリッジの `bridge100` を奪い、`en0` を外し、**Mac 本体の IPv4 が消える**。Apple に **FB25122122** として報告済み。再現ツール: `Prototypes/vmnet-bridge100-repro`。回復は `sudo ipconfig set en0 DHCP` か再起動。
- 新規に作ったものどうしなら、従来のブリッジと共存できる（`bridge100` と `bridge101` に分かれる）。
- インターフェースを開始したままプロセスが終了すると、そのサブネットはしばらく（数時間か再起動まで）`vmnet_network_create` が 1001 になる。ほかにも、socket_vmnet の起動と重なったときなどに、1001 が 1 分以上続くことがある。netd は、VM が接続している間は 2 秒おきに作成を再試行し続ける（その間に VM が送るフレームは捨てる）。失敗しても netd 自体は終了しない。
- `vmnet_network_configuration_set_ipv4_subnet` に渡すのはゲートウェイ（.1）。ネットワークアドレス（.0）を渡すとインターフェースの開始に失敗する。
- entitlement なしの ad-hoc 署名では `vmnet_network_create` が 1002 で失敗する。従来の bridged モードも、この署名なら root なしで起動した（未調査）。
