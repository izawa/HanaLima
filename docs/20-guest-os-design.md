# VM に入っている OS の表示

2026-11-27 の設計。Codex と対照設計をした。VM の概要タブに、どのテンプレートから作ったか（作成時の OS と版）と、いまゲストに入っている OS の版を出す。

## 1. 何を出すか

利用者が知りたいのは次の 3 つだった。

- 何のテンプレートから作った VM か（作成時のディストリビューションと版）
- いまの版は何か（ゲストの中で `do-release-upgrade` などをすると、作成時より新しくなっている）
- ディストリビューションは、インストールしてから変わらないはず

この 3 つに、概要タブの「由来とメモ」の 2 行で答える。

| 行 | 表示の例 | 決まる時点 |
|---|---|---|
| 作成元 | `template:ubuntu-lts`（作成時は Ubuntu 24.04 LTS） | 作成時に 1 回だけ。以後は変えない |
| OS | Ubuntu 26.04 LTS（2026-11-27 10:32 に確認）［確認］ | 確認するたびに書き換える |

ディストリビューションを別の項目として追いかけることはしない。OS の行は、確認のたびにディストリビューションの名前と版を一緒に読み直す。インストールし直して別の OS になった場合も、同じ処理で表示が変わる。

## 2. 作成時の版

`ubuntu-lts`、`debian`、`default` のように最新版を指すテンプレートは、作成の時点で、HanaLima のテンプレートの一覧がすでに版付きの名前（`ubuntu-24.04` など）に解決している。作成が成功したときに、この名前を VM の記録 `hanalima-vm.json` の `creationImage` に残す。テンプレートの名前自体が版付き（`fedora-44`）なら、その名前を残す。`docker` のように用途で名付けたテンプレートは版が分からないので、何も残さない。画面からの作成も MCP の作成も `recordCreation` を通るので、残す処理はそこに 1 つだけ置く。テンプレートの一覧はアプリの起動時に読んだものなので、記録の前に `limactl info` で読み直す（Homebrew の Lima のテンプレートは版ごとのフォルダにあり、アプリを開いたまま更新すると古いファイルを読むか、ファイルが無くなる）。読み直せなければ記録しない。残る弱点は、作成の途中（イメージのダウンロード中）に Lima を更新した場合で、作成のあとで読むので新しい版を記録しうる。作る前に版を決めて渡す形にすると、作成の流れ全体に手が入るわりに、起きるのはまれなので、採らなかった。

`limactl create` で作った VM や、この項目を足す前に作った VM には `creationImage` が無い。その VM でも、記録のテンプレートが版付きの名前ならそこから表示する。`ubuntu-lts` のような別名だけなら、作成時の版は添えない（「不明」と書いても、利用者が次にできることは無い）。lima.yaml の `images:` から作成時の版をさかのぼって推測することはしない。`images:` には CPU ごと、版ごとの候補が並んでいて、Lima はどの候補を実際に使ったかを記録していないからだ。

インストーラーの ISO から作った VM の作成元は、これまでどおり ISO のファイル名を出す。ISO の名前から版は推測しない（入れた OS と食い違いうる）。lima.yaml のイメージは、そのとき作ったダミーの 1 MiB のイメージなので、これも手がかりにならない。

## 3. いまの版

### いつ確認するか

VM が準備完了になったときに、自動で 1 回確認する（2026-11-27 ユーザー判断。Codex の案は「確認」ボタンだけで始め、自動は様子を見てから足す、だった）。読むだけで副作用が無く、何もしなくても「いまの版」に答えられるほうを採った。準備完了と判断する入口は、アプリの起動時に動いていた VM、`limactl watch` の `running`、`limactl start` の完了の 3 つで、同じ起動で 2 つが来ることがある。そこで入口を 1 つの関数にまとめ、起動ごとに 1 回だけ試す。`limactl watch` の `running` はポート転送の知らせのたびにも届くので、一度試したら、失敗しても次の起動まで試さない（`sh` の無いゲストで、ポートが開くたびに `limactl shell` を起動しないため）。例外は、アプリの起動時に動いていた VM だ。まだ起動の途中のことがある（Running になってから SSH が通るまで約 1 分）ので、そのときの確認は 1 回に数えず、あとから届く `running` でもう一度試す。確認の最中に届いた知らせは捨てず、その確認が失敗したら 1 回だけ試し直す。watch の知らせがアプリの一覧の更新より先に来たときは、一覧を更新してから確認する。

ゲストが自分で再起動したとき（`do-release-upgrade` の最後など）は、Lima から見ると Running のままだ。再起動のあとに `limactl watch` が出すのはポート転送の知らせ（`running` が真）で、ポートが開くたびに出るものと区別がつかない（2026-11-27、Alpine で 2 回確かめた）。自動の確認は一度読めたら次の起動まで読み直さないので、次に `limactl start` するかアプリを起動し直すまで、更新の前の版を出し続ける。そのため、OS の行に同じ確認を呼ぶ小さな「確認」ボタンを付ける。

次のときは確認しない。

- VM が一時停止中のとき（ゲストが止まっていて、`limactl shell` が返らない）。アプリの起動の直後は、一時停止しているかをまだ知らないので、HanaLima のドライバーの VM なら確認の前にドライバーに尋ねる
- 改名の最中
- VM が動いていないとき。確認のために VM を起動したり再開したりはしない

### 何を読むか

`limactl shell --tty=false <名前> sh -s` に決まったスクリプトを渡し、ログインユーザーで実行する（「今すぐ実行」と同じ経路）。`sudo` もネットワークも使わないので、隔離した VM（SSH が vsock）でも読める。最初に `uname -s` で OS を見分けるので、lima.yaml の `os:` は当てにしない。

| ゲスト | 読むもの | 出す名前の例 |
|---|---|---|
| Linux | `/etc/os-release`、無ければ `/usr/lib/os-release` の `PRETTY_NAME`。無ければ `NAME` と `VERSION_ID` | Ubuntu 26.04 LTS、Alpine Linux v3.22 |
| macOS | `sw_vers -productVersion`。IPSW の名前は使わない（復元に使った版で、その後の更新を反映しない） | macOS 27.0.1 |
| FreeBSD | `freebsd-version -u`（入っているユーザーランドの版。更新の直後は動いているカーネルの版と違うことがある） | FreeBSD 15.0-RELEASE-p1 |
| そのほか | `uname -s` の名前だけ | OpenBSD |

Windows のゲスト（Lima のテンプレートの一覧にある）で `sh -s` が動くかは確かめていない。動かなければ、確認は失敗して「未確認」のままになる。

ゲストの出力は信用しないデータとして扱う。os-release はシェルで読み込まず（`.` で読むと中身が実行される）、Mac の側で 1 行ずつ解析する。引用符とバックスラッシュはシェルの規則どおりに外す（単一引用符の中はそのまま、二重引用符の中は `\ " $ `` だけ、引用符なしは何でも）。標準エラーは見ない（`limactl shell` は、Mac の今のフォルダがゲストに無いと警告を出す）。出力は 16 KiB で切り、名前は 120 字で切って制御文字を落とす。期限は 15 秒で、過ぎたら `limactl` を終わらせる。

ゲストで版を読むコマンド（`sw_vers` など）が失敗したら、スクリプトを 0 以外で終わらせ、前の値を残す（版の無い名前で上書きしない）。

確認は VM を「処理中」にしない。準備完了の直後には、グループの一括起動の次の VM、MCP の構築の疎通の検査、隔離の初回起動の後処理が続く。確認が処理中の枠を取ると、これらが「処理中」で断られるからだ。読むだけなので、起動や停止と重なっても害は無い（停止と重なれば確認が失敗するだけ）。

### 何を残すか

成功したら、記録の `lastObservedOS` に、表示する名前と確認の日時（Mac の時計）を書く。書くのは確認が終わったときで、そのときのモデルの記録の `lastObservedOS` だけを差し替える。確認を始めたときの記録をそのまま書くと、そのあいだに変えたメモやグループを消してしまう。VM は記録の ID で引き直す（確認のあいだに改名されると名前が変わるため）。

失敗しても前の値は消さず、アラートも出さない。失敗の理由は残さない。自動の確認は頼まれずに走るので、失敗のたびに知らせると、止めたばかりの VM や一時停止の VM で邪魔になる。ボタンで確認したときも、表示の日時が変わらないことで分かる。

### どう出すか

一度でも確認できた VM は、何か月止めていても、確認した日時と一緒に値を出す。日数で期限切れにはしない。直後にゲストで更新されることもあるので、どの日数で区切っても正しくはならない。一度も確認できていなければ「未確認」と出し、止まっていれば「起動すると確認します」を添える。

## 4. 複製、スナップショット、改名

| 操作 | 作成時の版 | いまの版 |
|---|---|---|
| アプリの複製、`limactl clone` | 新しい記録になるので無くなる（作成元の行には「コピー元」を出す） | 「未確認」から始める |
| スナップショットを戻す（VZ の `DiskSnapshot`、Lima の `snapshot apply`） | 変えない | 消して「未確認」に戻す |
| 改名（アプリ、`limactl rename`） | 記録ごと付いていく | 付いていく |
| 休止から戻す | 変えない | 変えない（ディスクは同じ） |

複製した VM の確認の結果を親から写さないのは、スナップショットから複製するとディスクが過去に戻るからだ（Claude の最初の案は写すだった。Codex の案を採った）。複製の 2 つの経路（アプリの `InstanceCopy.finish` と、`reconcile` が `limactl clone` を見つけたとき）は、どちらも新しい記録を作るので、何もしなくても消える。ターミナルの `limactl snapshot apply` は HanaLima から見えないので、そのあとも古い値が残る。そのため、表示には必ず確認した日時を添える。

## 5. しないこと

- 定期的に確認しに行く、全部の VM を巡回する
- 更新の履歴を持つ
- 配布元に最新版を問い合わせる、更新を勧める
- ディスクのイメージを直接読む（動いていない VM の版を知るため）
- 確認のために VM を起動する
- OS ごとのアイコン（記録は表示する文字列だけで、ディストリビューションの ID を持たない。Claude の最初の案は ID と版を分けて持つだった。使い道が無いので Codex の案を採った）

## 6. 確かめること

Linux（Alpine、Ubuntu）、隔離した VM、ISO から入れた VM で、準備完了のあとに確認が通ること。FreeBSD と macOS は 2026-11-27 に確かめた（下の表）。macOS のゲストではスクリプトは通ったが、Lima の準備完了の知らせが来なかったので、自動の確認は走らず、「確認する」も出なかった（ボタンは準備完了の VM にだけ出す）。

2026-11-27 に確かめたこと（HanaLima のドライバー、Lima 2.3.0）:

| 確かめたこと | 結果 |
|---|---|
| Alpine をターミナルから起動する（`limactl watch` の `running`） | 「Alpine Linux v3.24」が記録された |
| Ubuntu をターミナルから起動する | 「Ubuntu 26.04.1 LTS」が記録された |
| 動いている VM がある状態でアプリを起動し直す | 起動の時点で読み直し、日時が新しくなった |
| Alpine を制御ソケットで一時停止してから、アプリを起動し直す | 確認は走らず（`limactl shell` も残らず）、記録の日時は変わらなかった |
| 動いている Alpine のゲストで `sudo reboot` する | VM は Running のまま。`watch` はポート転送の知らせを 4 件出したが、確認は走らなかった（一度読めているため） |
| FreeBSD（Lima の `template:freebsd`、QEMU、15.1）をターミナルから作って起動する | 準備完了の 1 秒後に「FreeBSD 15.1-RELEASE-p7」が記録された。ゲストの `freebsd-version -u` と同じ |
| macOS 27.0.1 のゲスト（Lima の vz、ディスクは外付けの HDD）を `limactl start` する | 10 分待っても Lima の起動スクリプトの完了の確認が通らず、`limactl start` は「`running` の知らせが来なかった」で終わった（VM は Running、シェルは通る）。確認のスクリプトを同じ経路で流すと `Darwin` と `27.0.1` を返した（終了コード 0）。準備完了にならないので、記録は「未確認」のまま |
| 止まっていて一度も確認していない VM（`template:ubuntu-lts`、版の記録より前に作った） | 作成元は版を添えず、OS は「未確認（起動すると確認します）」 |

レビュー（Codex、3 回）で採らなかったもの: `experimental/almalinux-kitten-10` の作成時の版が出ないこと。実験的なテンプレート 1 つのために、版付きの名前の規則（家族名のあとに数字）を変えるのは見合わない。
