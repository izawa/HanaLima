# VM のグループと一括操作の設計（2026-11-08）

VM が増えると、サイドバーの「仮想マシン」が縦に長くなる。そこで VM をグループにまとめ、グループごとに開閉できるようにし、グループの VM をまとめて起動・停止・休止できるようにする。この文書はその設計で、段階 1（グループとサイドバー）と段階 2（一括操作）は 2026-11-08 に実装した（6 章）。Claude の下書きと、Codex が同じ問いに独立に出した案を突き合わせ、食い違いの扱いを 9 章に置く。

## 1. 前提

### 1.1 Apple のヒューマンインターフェイスガイドライン

HIG の「Sidebars」の項には、次の 3 つがある。

- 項目が多いときは、開閉する階層（disclosure controls）でまとめて、サイドバーの縦の長さを抑える。
- 階層は 2 段まで。それより深くなるなら、サイドバーと詳細のあいだに一覧の列を挟む。グループの名前は短くする。
- サイドバーの中身や並びは、できれば利用者が変えられるようにする。

Apple のアプリで今回にいちばん近いのは、リマインダーの「グループ」である。リストをグループにまとめ、開閉三角で畳む。グループは「ファイル」>「新規グループ」で作るか、リストを別のリストに重ねて作る。メールのフォルダとメモのフォルダも同じ形をしている。

### 1.2 Lima にグループは無い

Lima 2.3.0 には、VM をまとめる仕組みもラベルも無い。`limactl list` の項目にもそれに当たるものは無く、絞り込みは `--filter`（yq の式）で行う。`limactl stop` は VM を複数受け付けるが、`limactl start` は 1 台だけである。

upstream では、VM・ディスク・ネットワークにラベルを付ける提案（lima-vm/lima#3240）が開いたままになっている。lima.yaml に利用者が自由に書ける `meta` の欄を足す PR（#4103）は、作業が止まったため 2026-10-13 に閉じられ、提案は #5610 に移った。lima.yaml の `param` にグループを書く方法は使えない。どこからも参照されない `param` のキーがあると、Lima は作成を断る。

したがって、グループは HanaLima の側で持つ。

## 2. 方針

- グループはフォルダと同じく、1 つの VM が入るのは 1 つのグループだけにする。Finder のタグのように 1 つの VM を複数の集まりに入れると、同じ VM がサイドバーの 2 か所に出て、一括操作の対象もあいまいになる。
- 階層は「グループ > VM」の 2 段だけにする。グループの中にグループは作れない。
- グループは HanaLima の表示と操作のためのもので、Lima の動きは変えない。ターミナルの `limactl` から見た VM は、これまでと同じである。

## 3. データの持ち方

### 3.1 2 か所に分ける

グループに関する情報は、次の 2 か所に置く。

| 置き場所 | 中身 | 正とする情報 |
|---|---|---|
| VM ごとの記録 `~/.lima/<名前>/hanalima-vm.json` の `group` | その VM が入っているグループの名前（入っていなければ無し） | どの VM がどのグループに入っているか |
| `~/Library/Application Support/HanaLima/groups.json` | グループの並び、開閉の状態、グループの中の VM の並びとグループに入っていない VM の並び（どちらも記録の ID で持つ）、まだ VM の無いグループ | 並びと開閉 |

所属を VM の記録に置くのは、記録が VM と一緒に動くからである。`limactl rename` では VM のフォルダごと移るので所属も付いていき、`limactl delete` では記録ごと消えるので、消えた VM がグループに残らない。

記録に書くのはグループの ID ではなく名前にする。`groups.json` が消えたり壊れたりしても、記録の名前からグループを作り直せるからである。ID で持つと、`groups.json` を失ったときに ID だけが残り、グループの名前を作り出すしかなくなる。名前で持つ代わりに、グループの名前を変えたときは、そのグループの VM の記録をすべて書き直す。VM の数だけ小さなファイルを書くだけで済む。グループの解除も同じく、VM の記録から `group` を消して回る。

複数のファイルを書くので、途中で失敗することがある。書き込みに失敗したら、それまでに書き直した記録を元の名前に戻し、名前の変更（解除）は行わなかったことにして知らせる。アプリが途中で終了したときは、新旧の名前の記録が混ざって残り、次の起動で 3.2 の規則により古い名前のグループも作り直される。利用者には 2 つのグループに分かれて見えるので、VM をドラッグして戻してもらう。めったに起きないので、自動では直さない。

### 3.2 食い違いの直し方

一覧を更新するたびに、記録と `groups.json` を次の規則で合わせる（`InstanceMetadata.reconcile` のあとに行う）。

- 記録にあるグループの名前が `groups.json` に無い: そのグループを末尾に足し、開いた状態にする（`groups.json` を失ったときや、別の Mac から VM のフォルダを持ってきたとき）。
- `groups.json` のグループに VM が 1 台も無い: そのまま残す（利用者が作った空のグループ）。
- グループの中の並び（グループに入っていない VM の並びも同じ）に、記録の ID が無い VM がいる: 記録に親があり、親が同じグループにいれば親のすぐ後ろに、そうでなければそのグループの末尾に名前順で足す（ターミナルの `limactl clone` の複製は前者になる）。並びにあって、もうグループにいない ID は捨てる。
- 名前の比較は大文字と小文字を区別しない。同じ名前のグループは 2 つ作れない。

`groups.json` は HanaLima だけが書く。アプリは同時に 1 つしか動かないので、書き込みの競合は考えない。

### 3.3 複製と作成

複製した VM は、元の VM と同じグループに入れ、元の VM のすぐ後ろに並べる。Finder でフォルダの中のファイルを複製すると、同じフォルダに残るのと同じである。

いまの実装では、複製で記録の中身が引き継がれない。アプリの複製（`InstanceCopy`）は新しい記録を作り、メモだけを渡している。ターミナルの `limactl clone` は記録ごと写すが、`reconcile` が「複製」と判断すると記録を作り直すので、メモ、テンプレート、Ansible の設定も落ちる。そこで、どちらの経路でも `group` を引き継ぐようにする。アプリの複製は、ディスクを写すあいだに時間がかかり、そのあいだに元の VM のグループが変わることがある。そのため、引き継ぐグループは複製を始めたときではなく、新しい記録を書く時点の元の VM の記録から読む。スナップショットから新しい VM を作る操作は複製を経由するので、同じ扱いになる。

作成画面には「グループ」の選択（「なし」とグループの一覧）を足し、`recordCreation` で記録に書く。サイドバーでグループを選んでいる状態、またはグループの VM を選んでいる状態で作成画面を開いたときは、そのグループを初期値にする。作成中でまだ記録の無い VM（`sidebarNames` が足しているもの）は、作成画面で選んだグループの中に表示する。

## 4. サイドバー

### 4.1 形

「仮想マシン」のセクションの中に、グループの行を並べ、その下にどのグループにも入っていない VM を並べる。

```
仮想マシン
  ▾ 📁 隔離テスト          2/3
       gateway      ● 実行中 · HANALIMA
       guest1       ● 実行中 · HANALIMA
       guest2       ○ 停止
  ▸ 📁 ディストリビューション  0/4
    hanalima-dev     ● 実行中 · VZ
    macOS27          ○ 停止
ストレージ
  …
ネットワーク
  …
```

- グループの行は、フォルダのアイコン（`folder`）、名前、右端に「実行中の台数／全体の台数」を出す。一時停止中と休止中は実行中に数えない。
- 開閉の状態は `groups.json` に覚える。
- グループの行も選べる。選ぶと、詳細の側にグループの画面（4.3）を出す。`SidebarItem` に `.group(String)`（名前）を足す。グループの名前を変えたら、選択も新しい名前に付け替える。一括操作の実行中は、そのグループの名前の変更と解除をできなくする（実行中の状態はグループの名前で持つため）。
- グループに入っていない VM も、ドラッグで並べ替えられる（4.2）。その並びも `groups.json` に記録の ID で覚え、並びに無い VM（新しく作った VM など）は末尾に名前順で足す。

サイドバー全体を 1 つの `NSOutlineView`（source list の形。Finder やメールのサイドバーと同じ部品）にし、`NSViewRepresentable` で `NavigationSplitView` のサイドバーの列に置く。「仮想マシン」「ストレージ」「ネットワーク」は `isGroupItem` の見出しの行、グループは開閉できる行、VM・ディスク・使用量・仮想ネットワークは選べる行にする。VM の行の中身は、いまの `SidebarRow`（SwiftUI）を `NSHostingView` で載せる。グループの行は、名前をその場で編集するため AppKit の `NSTextField` で作る。

最初は SwiftUI の `List` の中に `DisclosureGroup` を置く形で試作した（`Prototypes/sidebar-groups-spike` の `SPIKE_IMPL=swiftui`、2026-11-08）。選択、開閉、キー操作、ダブルクリックでの名前の編集は動いたが、ドラッグに問題が残った。同じグループの中の並べ替え（`onMove`）では挿入線が出るのに、別のグループやグループの外へのドラッグは行の `dropDestination` で受けるしかなく、そこでは線が出ず、VM の行に重ねると緑の十字（コピー）が出た（ユーザーが手で触って確かめた）。挿入位置を受け取る `ForEach` の `dropDestination(for:action:)` はこの入れ子のサイドバーでは働かず、行の `dropDestination` はカーソルを選べない。`NSOutlineView` なら、`validateDrop` でドロップの位置を付け替え（`setDropItem(_:dropChildIndex:)`）、操作（線か強調になる移動、緑の十字になるコピー、不可）を選べるので、どこへ動かしても同じ挿入線になる。AppKit 版の試作をユーザーが触り、「線での動かし方が統一されて触りやすい」としてこちらに決めた。

`NSOutlineView` は項目をオブジェクトの同一性で比べるので、行の項目はキー（`vm:<名前>`、`group:<名前>`）ごとにキャッシュして使い回す。選択（`SidebarItem`）と開閉（`groups.json`）は、モデルと `NSOutlineView` の両方向で合わせ、合わせている最中の通知は無視する。いまの `HANALIMA_SNAPSHOT_DUMP` は `NSTextField` から文字を拾うので、`NSHostingView` の行は写らない。`NSOutlineView` のデータから行を書き出す形に直す。

グループを 1 つずつ別の `Section(isExpanded:)` にする形（Finder のサイドバーの「よく使う項目」「場所」と同じ形）も考えた。しかし Finder のセクションはアプリが決めた区分で、利用者が作るフォルダではない。また、そうすると「ストレージ」「ネットワーク」と同じ高さに利用者のグループが並び、「仮想マシン」の見出しが無くなる。そのため採らない。

### 4.2 グループを作る、変える

| 操作 | 場所 |
|---|---|
| 新しいグループを作る | サイドバーの下の「＋」をメニューにして「新規仮想マシン」「新規グループ」を並べる。サイドバーの空いたところとグループの行のコンテキストメニューにも置く。グループに入っていない VM を、グループに入っていない別の VM に重ねてドロップすると、その 2 台で新しいグループを作る（リマインダーでリストを重ねてグループを作るのと同じ）。どの方法でも「新規グループ」（重なれば番号を付ける）という名前で作り、すぐ名前の編集欄を開く |
| VM をグループに入れる・出す | VM の行を、行と行のあいだ（どのグループでも、グループの外でも）へドラッグする。挿入線の位置に入る。グループの行へ落とすと、そのグループの末尾に入る。VM のコンテキストメニューに「グループへ移動 ▸」（グループの一覧、「新規グループ…」）と「グループから外す」 |
| 選んだ VM からグループを作る | サイドバーの複数選択は採らない（4.4） |
| VM の並びを変える | ドラッグ。グループの中の並びが一括起動の順番になる（5.2） |
| グループの並びを変える | グループの行をドラッグ |
| 名前を変える | グループの行をダブルクリックして直接編集。コンテキストメニューの「名前を変更」 |
| グループを解除する | コンテキストメニューの「グループを解除」。VM はグループの外に出るだけで、消えない |

グループの名前は空にできず、ほかのグループと同じ名前にもできない。

ドロップは `validateDrop` で次のように決める（試作で、判定の関数に全部のケースを渡して確かめた）。

| ドラッグするもの | ドロップ先 | 表示 | 結果 |
|---|---|---|---|
| VM | 行と行のあいだ（どの階層でも） | 挿入線 | その位置へ |
| VM | グループに入っていない VM の末尾より下、セクションのあいだ | 挿入線（末尾に付け替え） | 末尾へ |
| VM | グループとグループのあいだ | 挿入線（開いたグループのすぐ下ならその末尾、ほかはグループに入っていない VM の先頭に付け替え） | その位置へ |
| VM | ほかのグループの行の上 | グループの強調 | そのグループの末尾へ |
| VM | 自分がいるグループの行の上、自分の上、「ストレージ」などのセクション | 無し | 何も起きない |
| VM | グループの中の VM の行の上 | 挿入線（その VM の前に付け替え） | その VM の前へ（グループの中にグループは作らない） |
| VM | グループに入っていない VM の行の上 | 緑の十字 | 2 台で新しいグループを作る |
| グループ | グループとグループのあいだ | 挿入線 | 並べ替え |
| グループ | ほかのグループの行の上 | 無し | 何も起きない（入れ子は作らない） |

### 4.3 グループの画面

グループの行を選ぶと、詳細の側に次のものを出す。

- グループの名前と、VM の台数と状態の内訳。
- 一括操作のボタン: 「すべて起動」「すべて停止」「すべて休止」。
- VM の表: 並び順、名前、状態、仮想化方式、CPU・メモリ。行をダブルクリックすると、その VM を選ぶ。
- 一括操作の実行中は、どの VM まで進んだかと「中止」。終わったあとは、結果（成功、飛ばした VM と理由、失敗した VM とエラー）を次の一括操作まで残す。

### 4.4 サイドバーの複数選択は採らない

選んだ複数の VM からグループを作る操作には、サイドバーの複数選択が要る。しかし、いまの選択（`model.selection`）は 1 つで、詳細の画面も VM 1 台かディスクかネットワークのどれかを出す作りになっている。複数選択を入れると、2 台以上を選んだときに詳細に何を出すかを、すべての画面について決め直すことになる。グループはドラッグとメニューで作れるので、複数選択は入れない。

### 4.5 メニューバー

メニューバーのメニューは、いまは VM を平らに並べている。グループがあるときは、グループごとにサブメニューを作り、その中に「すべて起動」「すべて停止」「すべて休止」と、区切り線の下に VM を並べる。グループに入っていない VM は、いまと同じく平らに並べる。

## 5. 一括操作

### 5.1 操作の種類

| 操作 | 対象 | 順番 | 飛ばす VM |
|---|---|---|---|
| すべて起動 | 停止中と休止中の VM（休止中は再開） | グループの並び順 | 実行中、処理中、5.3 の理由で起動できないもの |
| すべて停止 | 実行中の VM（一時停止中を含む） | 並び順の逆 | 停止中、休止中、処理中 |
| すべて休止 | 実行中で、HanaLima のドライバーで動く VM | 並び順の逆 | Lima の vz・QEMU の VM、停止中、起動の完了前、処理中 |

一時停止と再開の一括操作は、最初は作らない（8 章）。

停止は VM ごとに `limactl stop <名前>` を呼ぶ。`limactl stop A B C` の形にしないのは、VM ごとの処理（`Operation`）と進み具合の表示を、いまの 1 台ずつの操作と同じものにするためである。一時停止中の VM の停止は、ドライバーが先に再開してから ACPI で止めるので、ほかと同じに扱える。

### 5.2 順番と、1 台ずつ実行すること

起動は、グループの並び順に 1 台ずつ行う。前の VM の `limactl start` が終わって（準備完了になって）から、次の VM を起動する。停止と休止は、並び順の逆に 1 台ずつ行う。

順番を並び順にするのは、利用者が順番を決められるようにするためである。たとえば、ゲスト専用ネットワークのルーターに指定した VM（出口を絞るゲートウェイ）は、その後ろの VM より先に起動しておく必要がある。後ろの VM が先に起動すると、DHCP で経路を受け取れないか、起動直後のプロビジョニングがインターネットに届かない。利用者がゲートウェイを先頭に並べておけば、起動はゲートウェイから始まり、停止はゲートウェイで終わる。`networks.json` の `router` から順番を推定する案もあるが、最初は作らない（8 章）。

同時に起動しないのは、次の理由による。

- メモリ: 10 台を同時に起動すると、Mac のメモリが足りなくなるおそれがある。
- イメージのダウンロード: 同じイメージを使う VM が同時に起動すると、同じダウンロードが重なる。
- 中止: 1 台ずつなら、中止すると「いま起動している VM が終わったら、次へ進まない」という分かりやすい動きになる。

1 台ずつだと時間はかかる。Alpine は 1 台 20〜40 秒、Ubuntu LTS は 1 分前後なので、5 台で数分になる。停止は 1 台 3〜5 秒、休止は 1 台 1〜2 秒で終わるので、問題にならない。

### 5.3 実行の前の確認をまとめる

いまの 1 台の起動（`AppModel.start`）は、次の順に確かめ、引っかかると利用者に尋ねるか断って、その場で終わる。

1. `refuseIfDiskUnusable`: ディスクが見つからない（外付けが外れている）、ほかの VM とディスクを共有している、インストール待ち（`pendingInstall`）。
2. `askIfDeletedNetworks`: 削除したネットワークを指す NIC がある。「NIC を外して起動」するか尋ねる。
3. `askIfConflicting`: socket_vmnet と HanaLima のネットワークを同時に使う。続けるか尋ねる。

尋ねる内容は、それぞれ 1 つの欄（`pendingConflictStart` など）に入る。一括で 1 台ずつこの関数を呼ぶと、2 台目の問いが 1 台目の問いを上書きし、利用者が答える前に次の VM へ進んでしまう。そこで一括操作では、実行の前に全部の VM を確かめて計画を作り、1 枚のシートで示してから実行する。

```
「隔離テスト」の 3 台を起動します

起動する（この順）
  1. gateway
  2. guest1
確認が必要
  ☐ guest2   削除したネットワーク「old」の NIC を外して起動する
起動しない
  dev-copy  ほかの VM とディスクを共有しています

メモリ: 起動する VM の合計 6 GiB（Mac の物理メモリ 64 GiB、実行中の VM 8 GiB）

                                  [キャンセル]  [起動]
```

- 「起動しない」には、1 の理由で断る VM、ほかの一括操作の対象になっている VM（5.5）、削除したネットワークの NIC を持つ休止中の VM（次の項目）を入れる。1 の理由の文は、1 台の起動で出す文と同じにする。
- 「確認が必要」は、2 と 3 の VM である。チェックは VM と確認の種類ごとに付け（1 台に 2 と 3 の両方があれば 2 つ）、すべてにチェックを付けた VM だけを起動する。既定ではチェックを付けない。いまの `start(_:confirmed:)` の `confirmed` は 2 と 3 をまとめて飛ばすので、一括操作では使わず、チェックを付けた確認だけを飛ばす。
- 2 の「NIC を外して起動」は、いまは `removeDeletedNICs(_:thenStart:)` が `limactl edit` のあとに `limactl start` を直接呼ぶ。一括操作では、NIC を外す編集、もう一度の確認、通常の起動の 3 つに分けて行う。休止中の VM には NIC を外す項目を出さず、「起動しない」に入れる。そのまま再開してもネットワークのソケットが無いので失敗し、NIC を外せば構成が変わって保存した状態から戻せなくなる（ドライバーが記録した構成と食い違い、起動を断る）からである。理由の文では「保存した状態を捨てる…」を案内する。
- 3 の socket_vmnet との同時使用は、いま実行中の VM だけでなく、計画の中でその VM より先に起動する VM も合わせて判定する。停止中の A が socket_vmnet を、B が HanaLima のネットワークを使うとき、実行中の VM だけで判定すると、どちらも確認なしになり、A を起動したあとで B が同時使用になるからである。
- 「再起動が必要」（`restartNeeded`）は、停止中の VM には付かないので、すべて起動では扱わない。実行中の VM を再起動する一括操作は作らない（8 章）。
- 起動する VM のメモリの合計と、実行中の VM のメモリの合計が、Mac の物理メモリを超えるときは、注意を出す。止めはしない（VZ のメモリはゲストが触った分だけ実際に使われるので、合計を超えても動くことが多い）。
- すべて停止とすべて休止にも、同じ形のシートを出す。停止で飛ばす VM は理由を出すだけで、確認の項目は無い。休止では、保存ファイルが VM ごとに残っていくので、VM のメモリの合計＋1 GiB の空きを、VM のフォルダのあるボリューム（`~/.lima`。ディスクを外付けに移した VM でも、保存ファイルは VM のフォルダに置く）について確かめ、シートに出す。足りなければ注意を出すが、止めはしない。各 VM の休止の直前にいまの 1 台の休止と同じ確認（その VM のメモリ＋1 GiB）が働き、足りなくなった VM からは休止せずに結果に書く。

計画はシートを出した時点のもので、実行中に VM をグループへ足したり外したりしても変わらない。計画には VM の名前と記録の ID を持つ。実行の直前に、各 VM をもう一度確かめ、状態が変わっていれば（ほかの操作で処理中になった、など）その VM を飛ばして結果に書く。名前の VM の記録の ID が計画と違えば（そのあいだに削除して同じ名前で作り直した）、別の VM なので飛ばす。名前が変わった VM は、ID から今の名前を引いて操作する。

### 5.4 失敗したとき

- 1 台の失敗では止めず、次の VM へ進む。ほかの VM に経路を配る VM（ゲートウェイ）が起動に失敗したら、後ろの VM を起動しても網に出られないので、本当は止めたい。しかし `networks.json` の `router` はアドレスで、どの VM かは書かれていない。VM を特定するには DHCP の予約（アドレスと MAC）と VM の NIC の MAC を突き合わせる必要があり、それは 8 章の「順番を推定する」と同じ仕事になる。そこで最初は止めずに進み、結果に失敗を出すだけにする。
- いまの `run` は、失敗すると VM ごとに警告のダイアログを出す。一括操作では出さず、グループの画面の結果にまとめる（`run` に、警告を出さない指定を足す）。
- 休止中の VM の再開に失敗したとき、1 台の起動では「保存した状態を捨てて起動」を尋ねる（`offerDiscardAfterFailedResume`）。一括操作では尋ねず、結果のその VM の行に「保存した状態を捨てて起動…」のボタンを出す。
- すべて休止で、最初の VM が Secure Enclave の鍵の問題（VZErrorDomain 11、この Mac で初めての保存を画面のロック中に行った）で失敗したときは、そこで止める。残りの VM も同じ理由で失敗するからである。

### 5.5 ほかの操作との関係

- 一括操作の実行中も、各 VM の処理は、いまの 1 台の操作（`operations[name]`）として表示する。サイドバーの VM の行には、いまと同じく「起動中…」などが出る。
- 一括操作の状態（計画、どこまで進んだか、結果）は、グループの名前ごとに `AppModel` に持つ。同じグループで一括操作が実行中のあいだは、そのグループの一括操作のボタンを使えなくする。別のグループの一括操作は同時に実行できる。
- 1 つの VM は 1 つのグループにだけ入るが、計画を作ったあとで VM を別のグループへ移すと、そのグループの一括操作の計画にも入りうる。そこで、実行中の一括操作の計画にまだ残っている VM は、ほかの一括操作の計画では「ほかの一括操作の対象」として起動しない側に入れる。1 台の操作は断らない（9 章）。
- 実行中でも、まだ順番の来ていない VM を 1 台ずつ操作することはできる。順番が来たときに、その VM が処理中であれば飛ばして結果に書く。
- 中止すると、いま処理している VM はそのまま終わるのを待ち、次の VM へは進まない。
- アプリを終了すると、一括操作は途中で終わる。次に開いたときに続きは行わない。
- メニューバーから一括操作を選んで、実行の前のシートを出す必要があるときは、メインウインドウを開いてグループの画面を選び、そこにシートを出す（休止の再開に失敗したときにウインドウを開くのと同じ仕組み）。

いまの 1 台の操作は、どれも結果を返さない。`run` は内部で `Task` を作って終わり、失敗を警告のダイアログで知らせる。休止（`hibernate`）と一時停止（`sendPauseOp`）は、それぞれ別に `Task` を作っている。一括操作は 1 台の終わりを待ってから次へ進むので、これらを「終わるまで待てて、成功・失敗と理由を返す」関数にまとめ直し、いまの 1 台の操作はその関数を呼ぶ形に書き換える。

まとめ直すときに、処理中の確かめをコマンドを作る前に行う。いまの `run(.start, on: name, client.start(name))` は、引数の `client.start(name)` を先に評価する。`LimaClient` のストリームは作った時点で `Task` を始めるので、`run` が処理中を見て何もせずに返っても、`limactl start` はもう起動している（ストリームが捨てられて SIGINT で止まる）。いまは処理中にボタンを使えなくしているので表に出ないが、一括操作では順番が来たときに処理中の VM がありうる。新しい関数は、処理中でないことを確かめて `operations[name]` を立ててから、コマンドのストリームを作る。

### 5.6 ログイン時の自動起動とは別

ログイン時の自動起動は、これまでどおり VM ごとの `limactl autostart` で、グループとは関係しない。グループの並び順を自動起動の順番にすることはできない。launchd は登録したエージェントを順番を決めずに起動するからである。

## 7. テスト

- 単体テスト（LimaKit）: 3.2 の食い違いの直し方（`groups.json` が無い、記録に無いグループがある、空のグループ、並びに無い VM、名前の大文字と小文字）。`reconcile` の複製と名前の変更で `group` が残ること。アプリの複製で `group` が引き継がれること。
- 単体テスト（計画）: 5.3 の計画づくりは、VM の状態、ディスクの置き場所、ネットワークを受け取って「起動する」「確認が必要」「起動しない」を返す純粋な関数にして LimaKit に置き、組み合わせを単体テストで確かめる。
- 画面確認: `HANALIMA_SNAPSHOT` に、グループの画面（`_SELECT=group:<名前>`）と実行の前のシートを足す。
- E2E（`GroupEndToEndTests`）: `hanalima-e2e-group-a`・`-b`（HanaLima のドライバー）と `-c`（vz）の Alpine を 1 つのグループに入れ、すべて起動が並び順に起動すること、すべて休止が `-c` を飛ばして逆順に休止すること、すべて起動で休止した 2 台が再開すること、すべて停止が逆順に止めることを確かめる。一括操作は `AppModel` にあり、E2E から直接は呼べないので、実行部分（計画を受け取り、1 台ずつ操作して結果を返すもの）を LimaKit に置き、アプリとテストの両方から使う。休止は `limactl` ではなくドライバーの制御ソケット（`DriverControl` の `hibernate`）で行うので、実行部分は 1 台の操作を関数として受け取り、`limactl` と制御ソケットのどちらも扱えるようにする。アプリは、その関数の中で `operations[name]` と画面の状態を更新する。単体テストでは偽の関数を渡し、順番、飛ばす規則、中止、途中の失敗を確かめる。

## 8. 後回しにすること

- 一時停止と再開の一括操作。休止と違い、一時停止は Mac のメモリを使ったままなので、まとめて行う場面が思い当たらない。使ってみて要るようなら足す。
- `networks.json` の `router` から起動の順番を推定すること。グループの画面で、並び順が「ルーターの VM が後ろの VM より後」になっているときに注意を出す形から始める。
- 再起動の一括操作。
- グループごとに CPU とメモリの合計を出すこと。

## 9. Codex の案との対照

Codex（read-only）に同じ問いを渡し、独立に案を作らせた。方針の大筋（「仮想マシン」のセクションの中に `DisclosureGroup`（のちに試作で `NSOutlineView` に変えた）、グループの画面、`SidebarItem.group`、1 台ずつの実行、実行の前に確かめて 1 枚にまとめる、`limactl stop A B` を使わない、`run` の警告を一括では出さない）は一致した。食い違った点と、この文書での扱いは次のとおり。

| 点 | Codex の案 | この文書 | 理由 |
|---|---|---|---|
| 所属の置き場所 | `groups.json` を正とし、グループの ID と VM の記録の ID で結ぶ | VM の記録にグループの名前を書く（3.1） | `groups.json` を失っても所属が残る。VM のフォルダを別の場所へ移しても所属が付いていく |
| ターミナルの `limactl clone` の複製 | 新しい ID なので、どのグループにも入れない | 元の VM と同じグループに入れる（3.3） | clone は記録ごと写すので、記録に名前を書く形では自然に引き継ぐ。Finder の複製と同じ動き |
| グループの外で消えた VM | 所属を「休眠」として残す | 記録ごと消えるので何も残らない | 記録に置く形では起こらない |
| 表示の並びと起動の順番 | 分ける。表示は名前順が既定で、起動の順番は別に指定する | 同じにする（5.2） | 見えている並びがそのまま実行の順番になるほうが分かりやすい。指定する場所が 1 か所で済む |
| 開閉の状態 | UserDefaults | `groups.json` | どちらでもよい。グループの情報を 1 つのファイルにまとめた |
| サイドバーの部品 | `List` の中の `DisclosureGroup` | `NSOutlineView`（4.1） | 下書きも同じ案だったが、試作でドラッグの表示が揃わず、AppKit に変えた |
| グループに入っていない VM の並び | `groups.json` に記録の ID で持つ | 同じ（4.1） | 下書きは名前順だったが、AppKit 版でどこへでも線で動かせるようにしたので、その並びも覚える |
| アプリを 2 つ同時に動かしたとき | ロックファイル、版番号、変更の監視 | 考えない（3.2） | HanaLima は 1 つのウインドウのアプリで、通常の起動では 2 つ目は開かない。書き込みは置き換え（atomic）で行い、壊れたファイルは読まない |
| まだ順番の来ていない VM の予約 | 予約して、1 台の操作や複製を断る | 予約しない（5.5） | 一括操作の途中でも、ほかの VM は普通に操作できるほうがよい。順番が来たときに処理中なら飛ばす |
| 一時停止・再開の一括操作 | 作る | 後回し（8 章） | 一時停止は Mac のメモリを使ったままで、まとめて行う場面がまだ見えない |
| どのグループにも入っていない VM | 「未分類」の見出しを付ける | 見出しを付けない（4.1） | グループの中の VM は字下げされるので区別できる。見出しを足すと、グループの無い利用者の表示が変わる |
| ゲートウェイの起動に失敗したとき | 後ろの VM を見送る | 止めずに進む（5.4） | どの VM がゲートウェイかを決めるには DHCP の予約と NIC の MAC を突き合わせる必要がある（Codex も、`router` はアドレスにすぎないと指摘した）。推定と一緒に後回しにする |

Codex の案と、この文書の下書きへの Codex のレビュー（read-only）の指摘で、この文書に取り込んだもの:

- `confirmed` が 2 種類の確認をまとめて飛ばすので、一括操作では確認の種類ごとにチェックを付ける（5.3）。
- `removeDeletedNICs(_:thenStart:)` は起動まで一続きなので、一括操作では分けて行う。休止中の VM は、NIC を外すと保存した状態から戻せなくなる（5.3）。
- 1 台の操作を、終わるまで待てて結果を返す形にまとめ直す（5.5）。
- メニューバーからの一括操作で確認が要るときは、メインウインドウを開く（5.5）。
- 計画に記録の ID を持ち、削除して同じ名前で作り直した VM を操作しない（5.3）。
- 計画を作ったあとで別のグループへ移した VM が、2 つの一括操作に入らないようにする（5.5）。
- socket_vmnet との同時使用を、計画の中で先に起動する VM も合わせて判定する（5.3）。
- `run` の処理中の確かめがコマンドの起動より後になっている（5.5）。
- グループの名前の変更・解除が途中で失敗したときの扱い（3.1）、複製の途中でグループが変わったときの扱いと、ターミナルの複製の並び（3.2、3.3）、名前を変えたときの選択と実行中の状態（4.1）。
- `DisclosureGroup` の選択とドラッグは試作で確かめる（4.1、4.2）。確かめた結果、ドラッグの表示が揃わず、`NSOutlineView` に変えた。
- 休止の空き容量は、VM ごとに 1 GiB を足すのではなく、メモリの合計＋1 GiB にする（5.3）。
- 実行部分は、休止のために制御ソケットも扱う（7 章）。

Codex は、いまの `updateMetadata` が処理中の VM を `reconcile` から外していることも指摘した。元の VM が処理中のあいだにターミナルで複製すると、`reconcile` は元の VM の記録を見ないので、複製を「名前の変更」と見て元の ID を渡す。元の VM の処理が終わったあとの更新では、どちらの記録も自分のフォルダを指しているので、一覧で先に来たほうが ID を持ち、もう一方が複製と見なされて新しい ID になる。名前順で複製が先なら ID が入れ替わり、ID で結んでいる VZ のスナップショット（`_hanalima-snapshots/<ID>`）と系譜が複製の側に付く。グループの名前は元の VM と複製で同じなので、グループには影響しない。これはグループと別の不具合なので、別に直す。
