# MCP で HanaLima を操作する設計

2026-11-11 時点の設計。まだ何も実装していない。ユーザーと決めたことは 10 章にまとめた。

## 1. 目標

ユーザーは MCP クライアント（Mac の上で会話の画面を持ち、AI と道具を取り次ぐプログラム）に、作りたい VM の構成を図や文章で渡す。
AI は HanaLima が出す道具（MCP の tools）を使い、その構成どおりのネットワークと VM を作り、起動し、つながりを確かめて報告する。
HanaLima は AI の API を呼ばず、認証情報も持たない。道具の一覧を MCP クライアントに渡し、呼ばれたら実行するだけにする。
この形は Rawgenzo の AI 委譲（`rawdev mcp`）と同じだが、コードは共有せず、HanaLima の中で独立に作る（3.2）。

もう一つの目標はトークンを少なく使うことである。VM の構築は待ち時間が長く、`limactl` の出力や lima.yaml をそのまま AI に見せると、
1 回の構築で数万トークンを使う。道具の数と説明を絞り、AI が細かい手順を組み立てなくて済む粒度にする（5 章）。

## 2. 図や文章からの依頼

ユーザーは構成を、VM とネットワークを線でつないだ図や、短い文章で渡すことがある。
図には、作るのに要る値が書かれていないことも、HanaLima ではそのまま作れないことが書かれていることもある。AI はそれを次の方針で宣言に直す。

1. **書かれていることは尊重する。** VM の名前、OS、つなぎ方、アドレス、固定の IP などは書かれたとおりにする
2. **書かれていないことは、AI が適切な値を想像して割り当てる。** CPU、メモリ、ディスク、テンプレートの版、サブネット（他と重ならないもの）、グループの名前など。割り当てた値は、尋ねずに最後の報告に並べる
3. **不可能な指示は、改定案と共にユーザーに確認する。** HanaLima で作れないもの（下の例）は、作れる形の案を添えて尋ね、答えを待ってから作る

`plan` はこの方針を支える形で結果を返す。宣言のうち、HanaLima が補った値（2 に当たるもの）と、作れない点とその改定案（3 に当たるもの）を分けて返す。
AI は 3 だけをユーザーに尋ね、2 は最後にまとめて伝える。補うたびに尋ねると往復が増えるためである。

作れない点の例:

- **サブネットの大きさ**: HanaLima のネットワークのプレフィックスは /16〜/28。/8 と書かれていたら /16 を案にする
- **既存のネットワークとの重なり**: サブネットの重なりは種類を問わず断る。空いている範囲を案にし、その範囲の中の固定の IP も合わせて案にする
- **隔離とドライバー**: 隔離（NIC 0 なし）は HanaLima のドライバーでしかできない。Lima の vz や QEMU と書かれていたら、どちらを優先するか尋ねる
- **ルーターの出口**: 出口を絞るゲートウェイの例は、既定の経路の NIC を出口にする。ルーターの VM に NIC 0 とブリッジの NIC が両方あると、どちらから出るかが決まらない。図がブリッジから出す形なら、ルーターの NIC 0 を外す案にする

図の線の読み方にも、書かれていないことが含まれる。たとえば、ゲストの線がゲスト専用ネットワークにしか引かれていないとき、Lima の VM は普通 NIC 0（usernet）で Mac とインターネットに届くので、
「ルーターだけが出口」と読むならゲストは隔離にする。これは 2（想像して割り当てる）として扱い、報告で「ゲストは隔離した」と伝える。

### 2.1 道具の呼び出しの流れ

作れない点をユーザーと決めたあとは、AI が呼ぶ道具は次の 5 回で済むようにする。

1. `hanalima_status`: 今ある VM・ネットワーク・グループを短い表で知る。名前の衝突とサブネットの重なりを避け、既存のブリッジのネットワークを見つけるため
2. `hanalima_plan`: 構成をひとまとまりの宣言（下の JSON）で渡し、計画、補った値、作れない点と改定案、確認が要る点を受け取る
3. `hanalima_apply`: 計画の ID を渡して実行を始め、ジョブの ID を受け取る
4. `hanalima_wait`: ジョブの終わりまで待ち、VM ごとに 1 行の結果を受け取る
5. `hanalima_check`: 「クライアントからほかのクライアントとルーターに届く」「クライアントの既定の経路がルーター」「ルーターから LAN に届く」などを確かめる

`apply` に `wait` の秒数を渡せば 3 と 4 は 1 回にまとまる。

宣言の例（ゲスト専用ネットワークにクライアント 2 台、ルーター 1 台がブリッジで LAN へ出る構成。`lan` は既にあるブリッジのネットワーク）:

```json
{
  "group": "example",
  "networks": [
    { "name": "inner", "mode": "guestOnly", "subnet": "10.20.0.0/16", "router": "router" }
  ],
  "vms": [
    { "name": "router", "template": "ubuntu-lts", "usernet": false,
      "nics": [{ "network": "inner", "ip": "10.20.0.1" }, { "network": "lan" }],
      "provision": [{ "example": "gateway" }], "gatewayAllow": ["*"] },
    { "name": "client1", "template": "ubuntu-lts", "isolated": true, "nics": [{ "network": "inner" }] },
    { "name": "client2", "template": "ubuntu-lts", "isolated": true, "nics": [{ "network": "inner" }] }
  ],
  "start": true
}
```

`isolated` は作成画面の「隔離した仮想マシンとして作る」と同じプリセット（ドライバー、NIC 0 なし、共有なし、NIC はゲスト専用だけ）で、
`usernet: false` は NIC 0 だけを外す。上のルーターのように、usernet なし・ゲスト専用・ブリッジを組み合わせた VM はまだ試していない
（ドライバーは `dns` を最初のゲスト専用ネットワークの netd で埋めるので、ルーター自身の名前解決も確かめる）。

ブリッジは Mac のネットワークに影響する（過去に Mac 本体の IPv4 を落とした）。宣言が既存のブリッジのネットワークを指すなら、
`plan` は「ブリッジにつなぐ」を確認の要る点として返す。ブリッジのネットワークを新しく作ることは MCP からはしない（7 章）。

### 2.2 HanaLima が埋める値

宣言に書かないことのうち、AI に考えさせなくてよいものは、HanaLima が今の画面と同じ規則で埋める。

- **ドライバー**: 既定の hanalima。隔離（`isolated`、`usernet: false`）はドライバーでしかできないので、ほかを指定すると作れない点として返す
- **固定の IP**: `ip` から MAC の DHCP 予約を作る。ゲスト専用ネットワークの `router` には VM の名前を書き、HanaLima がその VM の予約のアドレスに置き換える。DHCP のサーバーのアドレス（`gateway`）は、予約と重ならないものを HanaLima が選ぶ
- **隔離の手順**: Ubuntu 26.04 は systemd 256 以降なので、最初から NIC 0 なしで起動できる。Alpine など socat の導入に網が要るゲストは、NIC 0 を付けて 1 回起動し、止めて NIC 0 を外し、もう一度起動する。今の `pendingIsolation` は止まった VM の設定を書き換えるだけなので、この起動・停止・起動はジョブの工程として足す。AI はこの違いを知らなくてよい
- **ゲートウェイの許可リスト**: 今のプロビジョニングの例は引数を持たない。ゲートウェイの例は、許可先を書いた data の項目（`/etc/hanalima/gateway.conf`、既定はパッケージの取得先など）とスクリプトの 2 つでできているので、`gatewayAllow` があればその data の項目の中身を差し替えて入れる。ホスト名の許可は DNS で得た IP 単位の制御で、同じ IP の別のサービスとは区別できない（`help gateway` に書く）
- **起動の順序**: ルーターの VM をグループの先頭に置き、最初に起動する
- **共有フォルダ**: 隔離した VM は共有なし。隔離しない VM も、宣言に無ければホームを共有しない（7 章）
- **プロビジョニング**: 宣言に書けるのは同梱の例（と、その決まった引数）だけにする。任意のスクリプトは `run` で実行する（7 章の扱いを受ける）

## 3. プロセスの配置

```
MCP クライアント ─stdio─ hanalima-mcp ─Unix ソケット─ HanaLima.app ─ limactl / netd / ドライバー
       │
       └─ 外向きの HTTPS ─→ AI の API
```

| 登場人物 | 実体 | 役割 |
|---|---|---|
| `hanalima-mcp` | アプリに同梱する実行ファイル（`Contents/Helpers/`）。MCP クライアントが子プロセスとして起動する | 標準入出力の MCP（JSON-RPC 2.0）を受け、アプリのソケットへ中継する |
| HanaLima.app | アプリ | 設定「AI からの操作を受け付ける」がオンのとき、`~/Library/Application Support/HanaLima/agent.sock`（0600）で受ける。検証・計画・実行・画面への反映 |

外から Mac に入る接続は無い。Rawgenzo と同じく、リモート MCP（インターネットから届く URL）は採らない。

### 3.1 実行をアプリに集める理由

Rawgenzo の `rawdev` は、アプリが居なければ自分で処理する。HanaLima で同じことをすると、次の処理を 2 か所に持つことになる。
これらは今 `AppModel` にあり、LimaKit や NetworkKit には無い。

- 作成の後始末: 記録（`hanalima-vm.json`）、グループへの所属、ディスクの移動、`pendingIsolation`
- 起動の前の確認: 削除したネットワークの NIC、socket_vmnet との同時使用、休止から戻せないときの扱い
- 処理中の印（`Operation`）: 起動・停止・複製・削除が重ならないようにする
- 一括操作の事実集めと、実行の直前の確かめ直し

`GroupPlan` と `GroupRunner` そのものは LimaKit にあるが、計画に要る事実を集め、実行の直前に確かめ直し、1 台ずつの操作につなぐのは `AppModel` である。

そこで、実行はアプリだけが行う。アプリが動いていなければ、`hanalima-mcp` はアプリを起動し、ソケットが現れるのを待つ。
設定がオフなら起動せず、オンにする手順を返す。AI の操作は画面にもそのまま現れ、人がアプリで同じ VM を触っても処理中の印で重ならない。
今のアプリは起動時に自分を前面に出す（`NSApp.activate()`）ので、画面に出さずに起動するには手直しが要る。

ただし、今の `AppModel` の操作はそのまま道具にできない。多くは結果を返さず、確認が要ればダイアログを出す（`start` は確認の欄に印を付けて戻る）。
MCP には、操作の結果を待てて、確認の要る点を値として返す実行の層が要る。画面のボタンもこの層を呼ぶ形にすると、画面と AI の振る舞いがずれない。
実装の大半はこの層の切り出しになる見込みである。

### 3.2 MCP の部分は HanaLima の中に作る

道具の定義、入力の検証、影響の段階、監査ログ、MCP のサーバー（stdio の JSON-RPC）、Unix ソケットは、HanaLima の新しいターゲットとして作る。
Rawgenzo の `OperationSurface` は同じ役割を持つが、パッケージとしては共有しない（2026-11-11 ユーザー判断）。
設計の考え方（影響の段階、取りに来る形の観測、目標で指示する操作）は参考にする。外部の依存は増やさず、Foundation だけで書く。

### 3.3 MCP クライアントへの登録

アプリは起動するたびに `~/.hanalima/mcp.json` を確かめ、無ければ同梱の `hanalima-mcp` を登録した内容で書く。
最後に起動した .app の `hanalima-mcp` に向け直し、.app の外の存在するファイルを指していれば、人が書き換えたものとして触らない（Rawgenzo の `MCPConfigFile` と同じ規則）。
ユーザーは MCP クライアントにこのファイルを読ませる。

## 4. 道具の一覧（案）

名前の前に `hanalima_` を付ける（MCP クライアントの中で、ほかのサーバーの道具と区別しやすい）。

| 道具 | 影響 | 内容 |
|---|---|---|
| `status` | 読む | VM・ネットワーク・グループ・実行中のジョブを 1 行ずつ。`name` を渡すとその 1 つの詳細（NIC、アドレス、記録、スナップショット） |
| `templates` | 読む | テンプレートを `query`（`ubuntu`、`alpine` など）で絞って返す。全件は返さない |
| `examples` | 読む | プロビジョニングの例の id と 1 行の説明、引数（`gateway` の `allow` など） |
| `plan` | 読む | 2 章の宣言を検証し、計画（作る・変える・そのまま・断る）と確認が要る点を返す。何も変えない |
| `apply` | 作る | `plan` の ID と、確認が要る点への承認を受けて実行を始める |
| `vm` | 取り消せる変更 | `start`・`stop`・`restart`・`pause`・`resume`・`hibernate` を VM に。グループに対しては、今の一括操作がある `start`・`stop`・`hibernate` だけ（順序も同じ） |
| `snapshot` | 作る・戻す | `create`・`list`・`apply`。`apply` は今のディスクを捨てるので確認が要る |
| `wait` | 読む | ジョブの終わりか `timeout`（秒）まで待ち、短い結果を返す |
| `check` | ゲストで読む | 決まった検査だけを実行する: VM 間の到達（ping）、名前解決、TCP の接続、HTTP の取得、DHCP のリース |
| `run` | ゲストで実行 | VM でシェルのスクリプトを実行し、終了コードと出力の末尾を返す（今すぐ実行と同じ経路）。MCP で作った VM ならそのまま、人の VM はアプリでの承認を受けてから（7.2） |
| `delete` | 消す | MCP で作った VM とネットワークだけ（7.2）。それ以外は理由を返して断る |
| `help` | 読む | 話題（`topology`、`isolation`、`gateway`、`errors` など）ごとの詳しい説明 |

12 個。VM の設定の細かい変更（CPU、メモリ、ポート転送、共有フォルダ）は、項目ごとの道具を作らず、同じ宣言を `plan` に渡し直して差分として扱う。
道具を項目ごとに増やすと、一覧の説明だけで毎回のトークンが増えるためである。

宣言と今の状態の差分を当てるには、書かなかった項目を「そのまま」「既定に戻す」「消す」のどれと読むか、実行中や休止中の VM をどう変えるかを決める必要がある。
最初の版では作ることだけを扱う。宣言にある VM やネットワークが既にあれば、中身が宣言と合うなら「そのまま」、合わなければ違いを示して断る。
変更は、差分の規則を決めてから足す。

## 5. トークンを減らす工夫

道具の一覧と、MCP のサーバーが返す AI への説明（`instructions`）は、会話のたびに毎回送られる。
道具の結果は会話の履歴に残り、以後の往復でも毎回送られる。この 2 つを小さくする。

### 5.1 一覧と説明を小さく保つ

- 道具は 12 個にとどめ、説明は 1〜2 文にする。注意事項は `help` に置き、要るときだけ AI が取りに来る
- 入力のスキーマは浅くする。宣言の細部は JSON Schema に書き込まず、`plan` の説明に短い例を 1 つ置く。構築のたびに要る情報なので、`help` に置くと往復が 1 回増える
- `instructions` は 10 行程度: 「構成を作るときは `plan` → `apply` → `wait` → `check` の順」「図や文章は 2 章の方針で読む（書かれたことは尊重、書かれていないことは補って最後に報告、作れないことは改定案と共に尋ねる）」「長い処理は `wait` で待つ」「`help` に詳細」

### 5.2 結果を短く返す

- 一覧は表の形（1 項目 1 行、列はタブ区切り）で返し、JSON のキーを繰り返さない。既定値と同じ項目は書かない
- 変更の結果は差分だけ（「c1: 作成 → 起動 → 準備完了 10.0.0.23」）。設定全体や lima.yaml は返さない
- 失敗は、場所（`$.vms[1].nics[0].ip`）、理由、直し方を 1 行で返す。ログは失敗したときだけ、エラーの行と末尾に絞り、字数の上限（例: 4 KB）を超えたら切って「続きあり」と書く。`run` の出力も同じ上限にする
- `templates` は絞り込みを必須にし、`limactl info` の全件（数千トークン）を返さない
- 画像（画面のサムネイル）は返さない。画面を見る必要がある作業は道具にしない

### 5.3 往復を減らす

- 宣言をまとめて受ける（2 章）。VM を 1 台ずつ作る道具にすると、台数と手順の分だけ往復と確認が増える
- 待つのはサーバーの側で行う。`wait` は終わるか `timeout` まで返さない。AI が数秒おきに状態を聞くと、その分の結果が履歴に溜まる。`apply` と `vm` も `wait`（秒）を受け、その間に終われば結果をそのまま返す
- 途中で失敗しても、同じ宣言の `plan` → `apply` で残りだけを実行できるようにする。名前だけでは「作り済み」と「作りかけ」（作成は済んだが記録の保存や最初の起動が済んでいない）を区別できないので、ジョブは工程ごとの進み具合をアプリの中に記録し、作りかけの VM は続きから進める。同じ計画の `apply` が 2 回届いたら、新しいジョブを作らず実行中のジョブを返す
- `check` は検査をまとめて受け、通ったものは件数だけ、落ちたものは 1 行ずつ返す

### 5.4 見積もり（測っていない）

2.1 の例で、道具の一覧と説明が約 2,000 トークン、5 回の呼び出しの結果が合わせて約 2,000 トークンと見込む。
AI がシェルで `limactl` を直接使い、lima.yaml を読み書きしてネットワークを手で作る場合は、出力とファイルの中身で数万トークンになる見込みである。
実装したら、Rawgenzo の `mcp-log.jsonl` と同じく道具ごとの入力と結果の字数を記録し、試験の会話で測る。

## 6. 長い処理

作成と起動は、イメージの取得を含めて数分かかる。`apply` と `vm` はジョブの ID をすぐ返し、`wait` で待つ。

- `wait` の `timeout` は既定 120 秒、上限 600 秒。時間切れでも失敗にはせず、途中の状態（「c1: 起動中 2/3」）を返す。AI はもう一度 `wait` を呼ぶ
- MCP クライアントの道具の呼び出しに時間の上限があるかは確かめていない。上限より短い `timeout` を既定にするため、実装の前に確かめる
- MCP の進捗の通知（`notifications/progress`）は使えるなら使うが、AI の会話には入らないので、トークンの節約には関係しない
- `wait` の時間切れ（AI が待つのをやめる）と、ジョブの中止（`vm` の `cancel` など）は別のものにする。`run` と `check` も長くなりうるので、同じくジョブにする
- ジョブはアプリの中にあり、`hanalima-mcp` が終わっても続く。アプリを終了したときに実行中の `limactl` がどうなるかは確かめていない（終了時に止めているのは `limactl watch` などの常駐する子プロセスだけ）。終了の前に実行中のジョブがあれば尋ね、次の起動で工程の記録から途中の状態を `status` に出す

## 7. 安全の決まり

### 7.1 影響の段階と扱い

| 段階 | 道具 | 扱い |
|---|---|---|
| 読む | `status`・`templates`・`examples`・`plan`・`wait`・`help` | 許す |
| 作る・取り消せる変更 | `apply`・`vm`・`snapshot create` | 許す。画面に「AI が操作中」と出す |
| ゲストで実行 | `check`・`run` | 許す。ゲストの中だけで動く。ただし隔離しない VM はホームの共有と NIC 0 から Mac に届く（docs/06） |
| 戻す・消す | `snapshot apply`・`delete` | MCP で作ったものだけ。`plan` と同じく確認の要る点として返し、承認を受けてから行う |
| Mac に影響する | ブリッジ（`en0` など）、ホームの書き込み共有、ポート転送の公開 | `plan` で確認の要る点として返す。ブリッジのネットワークは MCP からは作らない |
| 道具にしない | sudo の要る操作、socket_vmnet の導入、アプリの設定の変更 | 一覧に出さない |

確認の要る点は `plan` の結果に並べ、`apply` は承認の無い計画を断る。
ただし、`apply` に載ってくる承認は AI が送ったものであり、人が確かめたとは限らない。
MCP クライアントは道具の呼び出しのたびに人の許可を求めることができるが、それはクライアントの設定次第で、HanaLima からは分からない。
そこで、確認の要る点（戻す・消す・ブリッジにつなぐ）を含む計画は、アプリが自分の画面で人に承認を求める（計画の中身を見せ、「実行」を押してもらう）。
`apply` はそれまで待つか、承認待ちとして返す。確認の要らない計画は、AI の `apply` だけで進む。
画面の確認ダイアログ（削除したネットワークの NIC、socket_vmnet との同時使用、保存した状態を捨てる）は、すべてこの形に置き換える。
`GroupPlan` がすでにこの形（先に全部を確かめ、確認の要るものを並べ、実行の直前に確かめ直す）なので、それに合わせる。

### 7.2 MCP で作ったものに印を付ける

MCP で作った VM の記録（`hanalima-vm.json`）とネットワーク（`networks.json`）に `createdBy: "mcp"` を書く。
AI が状態を変える道具（`vm`、`run`、`snapshot`、`delete`）と、宣言で既存のネットワークに NIC や予約を足すことは、既定ではこの印のあるものだけを対象にする。
人の VM を AI が止めたり、その中でスクリプトを実行したりできないようにするためで、開発中の試験でもユーザーの VM を守れる。
印の無いものを対象にした計画やジョブは、7.1 と同じくアプリの画面で人の承認を求める。消すことは、印の無いものには承認があってもせず、人がアプリで行う。
読む道具（`status` など）は印を問わない。

### 7.3 計画を飛ばさせない

`apply` は `plan` が返した ID だけを受ける。ID は宣言と、計画を作った時点の状態から作る。
記録の ID は設定を変えても変わらないので、状態には lima.yaml の中身、実行・停止・休止の別、ネットワークの内容、グループの並びも含める。
`apply` の直前と各工程の前に状態を確かめ直し、違えば止めて `plan` のやり直しを求める（その間に人がアプリで変えた場合）。
ネットワークを保存すると netd が新しい設定で起動し直し、それを使う実行中の VM は再起動するまでつながらない。VM ごとの処理中の印はこれを防がないので、ジョブはネットワークを変える工程の前に、使っている VM を確かめる。

### 7.4 ソケットの相手と、ゲストからの出力

`agent.sock` は 0600 なので同じユーザーのプロセスなら誰でもつなげる。これは同じユーザーで動くプログラムがすでに `limactl` を直接使えるのと同じ範囲で、それ以上は守らない。
アプリは、つないできたプロセスの実行ファイル（`LOCAL_PEERPID` から引く）を監査ログに書く。設定をオフにしたら、つながっている接続を切り、実行中のジョブは最後まで進める。

`run`・`check` の出力とゲストのログは、ゲストの中のプログラムが書いたものである。AI への指示のように読める文が入っていても、データとして扱うよう `instructions` に書く。
出力に秘密（鍵、トークン）が入りうるので、監査ログには出力そのものを書かず、字数と終了コードだけを書く。

## 8. 段階的な進め方（案）

| 段階 | 内容 | 確かめ方 |
|---|---|---|
| 0 | MCP のターゲット（3.2）、アプリのソケット、`hanalima-mcp` の中継、`~/.hanalima/mcp.json` だけを作る。道具は `status`・`templates`・`help`。並行して、結果を待てる実行の層を `AppModel` から切り出す（3.1） | MCP クライアントから一覧が読めること。一覧の字数を測る |
| 1 | `vm`・`wait`。確認の要る点の形（`GroupPlan` の流用） | 既存の VM の起動・停止。`hanalima-e2e-*` で試す |
| 2 | `plan`・`apply`（宣言からの構築）、`createdBy` の印、`delete` | 図や文章で構成を新しい会話で頼み（ブリッジは試験用のネットワークか、ユーザーの確認を得てから）、作れない点の確認と補った値の報告が 2 章の方針どおりか、道具の記録で往復と字数を見る |
| 3 | `check`・`run`・`snapshot` | ゲートウェイの許可リストが効くことを AI が確かめられること |
| 4 | 試験の記録をもとに説明と結果の形を直す | 同じ依頼で字数が減ること |

試験の VM は `hanalima-e2e-*`、ネットワークは使い捨てのサブネットにする。

## 9. 確かめていないこと

- MCP クライアントの道具の呼び出しに時間の上限があるか（6 章の `timeout` の既定値を決めるため）
- 5.4 の字数は見込みで、測っていない
- usernet なし・ゲスト専用・ブリッジを組み合わせた VM の起動と名前解決（2.1）
- MCP クライアントが `~/.hanalima/mcp.json` をどう読むか（読み込むファイルを指定するオプションか、作業フォルダの設定ファイルか。後者ならファイル名の決まりに合わせて同じ内容を置く）
- アプリを終了したときに、実行中の `limactl` の子プロセスがどうなるか（6 章）

## 10. 決めたこと（2026-11-11 ユーザー判断）

1. **アプリが居ないとき**: `hanalima-mcp` がアプリを起動し、ソケットが現れるのを待つ（3.1）
2. **MCP の部分**: Rawgenzo とは独立に、HanaLima の中に作る（3.2）
3. **ゲストでの実行（`run`）**: 道具に入れる。MCP で作った VM ではそのまま、人の VM ではアプリでの承認を受けてから（7.2）
4. **消す道具**: `delete` を出す。対象は MCP で作った VM とネットワークだけ（7.2）
5. **人の VM**: `vm`・`run`・`snapshot` は、アプリでの承認を条件に人の VM にも使える（7.2）
6. **人の承認**: 確認の要る計画は、アプリの画面で人に承認してもらう（7.1）
7. **MCP クライアントへの登録**: アプリが `~/.hanalima/mcp.json` を書き、MCP クライアントに読ませる（3.3）
8. **図や文章の読み方**: 書かれていることは尊重する。書かれていないことは AI が適切な値を想像して割り当てる。不可能な指示は改定案と共にユーザーに確認する（2 章）

まだ決めていないこと: 最初に試す依頼（8 章の段階 2 で使う）。
