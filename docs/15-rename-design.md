# VM の名前の変更

2026-11-16 の設計。作った VM の名前を、HanaLima の画面から変えられるようにする。Lima の `limactl rename` を呼び、Lima がしないことを HanaLima が前後で補う。

## 1. `limactl rename` がすること

Lima 2.3.0 のソース（`pkg/instance/clone.go`、`cmd/limactl/clone.go`）と、使い捨ての VM での実験で確かめた。

- 断るのは実行中の VM だけ。停止中なら、休止中（Lima からは停止中に見える）でも改名する
- フォルダを一度に改名するのではなく、中のファイルを 1 つずつ新しいフォルダへ `rename` し、最後に古いフォルダを消す
- 保護の印（`limactl protect` の `protected`）、QEMU の TPM の状態、`.pid`・`.sock`・`.tmp` のファイルは移さず、古いフォルダごと消す
- `vz-identifier` は空にする（次の起動で作り直す）
- サブフォルダがあると、移し先に権限 0 のフォルダを作り、その中へ移せずに止まる。実験では、ディスクと lima.yaml が新しいフォルダへ、残りが古いフォルダに分かれた
- 自動起動の登録（`~/Library/LaunchAgents/io.lima-vm.autostart.<名前>.plist`）には触れない
- `networks:` で MAC を書いていない NIC の MAC は、lima.yaml のパスから作るので、改名で変わる（実験で `52:55:55:46:3a:1c` が `52:55:55:a8:aa:ce` になった）。lima.yaml に書いた MAC は変わらない
- ホスト名は次の起動で `lima-<新しい名前>` になる

## 2. 名前が変わっても今のままでよいもの

- VM ごとの記録 `hanalima-vm.json` はフォルダと一緒に移る。記録の照合（`InstanceMetadata.reconcile`）は、元のフォルダに同じ ID の VM がいなければ改名と見て ID を保つ。ID で引くもの（`_hanalima-snapshots/<ID>`、`groups.json` の並び、MCP の台帳）はそのまま使える
- 外付けのディスクはリンクが移り、目印は `ExternalDisk.claimIfOrphaned` が新しいフォルダへ付け替える。`HanaLima Disks/<古い名前>` のフォルダ名は変えない（変えると失敗する箇所が増えるだけで、得るものがない）
- Ansible のインベントリは一覧が変わるたびに書き直す
- MCP の台帳は記録の ID で持つ

## 3. 改名できない VM

`renameBlocker` が理由を返し、シートに出す。

| 条件 | 理由 |
|---|---|
| 実行中、処理中、自動起動の切り替え中、どれかの VM の複製中、ほかの VM の改名中 | Lima が断る。処理中は他の操作と重ねない。複製は終わるまで複製元のフォルダを読む |
| 休止中 | 保存した状態は `vz-identifier` と MAC に結びつくので、改名で使えなくなる。アプリの印でなく、保存したファイルがあるかで判定する |
| 救出起動・インストールのドライバーが動いている | Lima からは停止中に見えるが、ディスクを使っている。アプリを終了しても動き続けるので、プロセス（`DriverControl.hostedPID`）で判定する |
| OS のインストールが終わっていない、救出起動かインストールのウインドウが開いている | ウインドウのセッションが名前とフォルダで VM を指す |
| 外付けのドライブが外れている | ディスクの目印を直せない |
| 保護している | Lima が保護の印を捨てる。`limactl unprotect` してからにしてもらう（2026-11-16 ユーザー判断） |
| フォルダにサブフォルダがある | Lima が途中で止まり、フォルダが 2 つに分かれる。QEMU の TPM の状態もサブフォルダなので、ここで断る |
| macOS のゲスト | `vz-identifier` が空になったときの影響を確かめていない |
| `networks:` が lima.yaml の外（テンプレートの `base` や Lima の既定の設定）にある | 下の MAC の書き込みで、NIC を lima.yaml の位置で指せない |

新しい名前は、作成と同じ規則（`CreateOptions.isValidName`）に合い、どの VM のフォルダとも大文字と小文字を区別せずに重ならないこと（APFS の既定は区別しない。大文字と小文字だけを変える改名も、Lima が「すでにある」と断る）。ソケットのパス（`<VM のフォルダ>/ssh.sock` に 17 文字を足したもの）が 104 バイト未満であること（Lima と同じ判定）。

## 4. 手順

古い名前と新しい名前の両方を処理中にして、次の順に行う。

1. `networks:` の NIC のうち MAC を書いていないものに、いまの MAC を `limactl edit --set '.networks[<i>].macAddress = "…"'` で書く。DHCP の予約、リース、ブリッジ先の LAN のルーターの予約がそのまま効く。`networks.json` は変えないので、netd は起動し直さず、同じネットワークの実行中の VM も切れない（書く範囲は 2026-11-16 ユーザー判断: MAC を書いていない NIC すべて）
2. 自動起動が登録されていれば（前の改名で登録し直せなかった印が記録に残っていればそれも）、記録に `autostartAfterRename` を書いてから、古い名前の登録を外す
3. `limactl rename <古い名前> <新しい名前> --tty=false`
4. 外付けのディスクの目印を付け替え、自動起動を新しい名前で登録し、記録のフォルダを新しいものに直して印を消す。名前をキーにしたアプリの状態（選択、操作のログ）を移す。目印を最初にするのは、残りが失敗しても、ディスクを共有する CLI の複製に目印を取られないため

失敗したとき:

- 手順 3 より前なら、自動起動を元に戻す。手順 1 で書いた MAC は、それまでと同じ値なので残してよい
- 手順 3 のあとでアプリが終了したか、手順 4 の登録に失敗しても、印は記録にあってフォルダと一緒に移っている。一覧の更新で、印のある停止中の VM を自動起動に登録し直す（アプリの起動ごとに 1 回だけ試す。失敗し続けても繰り返さない）
- 手順 3 の途中で失敗し、フォルダが 2 つに分かれたときは、両方のパスを示して止める。自動では直さない。3 章でサブフォルダを断るので、通常は起きない

改名の間、一覧の更新は改名が終わるまで待ち、改名の前に始まった一覧の結果は捨てる。途中の一覧では VM のファイルが 2 つのフォルダに分かれていて、記録の照合、グループの並び、外付けのディスクの目印と共有の判定が誤った結果を書くため（記録が 2 つの名前のどちらにも見えないと、並びから VM が落ちる。古いフォルダのリンクが消えると、ディスクを共有する複製が目印を取る）。改名中の VM の記録への書き込み（メモ、グループ、Ansible）も断る。

## 5. 画面

VM の右クリックと詳細のメニューの「名前を変更…」でシートを開く。新しい名前をその場で確かめ、改名できない理由を出す。改名すると次の起動でホスト名が変わること（ゲスト専用ネットワークの DNS、Ansible、スクリプトの中の古い名前）を注記する。

MCP には最初の版では入れない。入れるときは `vm` の `action: rename` にする。

## 6. 試験

- 単体: 改名できない条件、MAC を書く式、ソケットの長さ、大文字と小文字だけ違う名前
- E2E（`RenameEndToEndTests`）: 使い捨てのゲスト専用ネットワークで予約した IP の Alpine の VM（HanaLima のドライバー）にスナップショットを作り、グループに入れて改名し、起動する。同じ IP、ホスト名 `lima-<新しい名前>`、同じ記録の ID、スナップショットとグループが残ることを確かめる。後片付けは両方の名前で行う
