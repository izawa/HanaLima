# VM をホストから切り離せるか（調査結果）

調査日: 2026-10-14 / 環境: macOS 27.0.1 (Apple Silicon), Lima 2.2.1

## 1. 目的

マルウェアの疑いがあるものを VM の中で試すとき、Mac（ホスト）に攻撃や感染が及ばないようにしたい。案として、HanaLima に「ゲスト同士だけで通信でき、Mac は参加しない」ネットワーク（hanalima-netd の中で vmnet を使わずに VM 同士のフレームを中継するスイッチ）を足すことを考えた。ただし、Lima の VM にはそのネットワークとは別にホストとつながる経路があるので、まずそれぞれを設定で閉じられるかを確かめた。

## 2. 結論

- **Lima 2.2.1 では、標準の NIC 0（ユーザーモードのネットワーク、SLIRP）を外す設定がない。** `plain: true` でも残る。
- NIC 0 を通って、ゲストから **インターネット、LAN、Mac の `127.0.0.1` だけで待ち受けるサービス** に届く。ゲストから見たゲートウェイ（`192.168.5.2` = `host.lima.internal`）が Mac のループバックにつながっているため（Lima の仕様）。
- 共有、ゲストのポートの自動転送、ゲストエージェントは、設定で閉じられる。
- したがって、**Lima を改造せずに VM を Mac から切り離すことはできない。** ゲスト専用のネットワークを足しても NIC 0 が残るので、隔離にはならない。HanaLima では作らない（Lima に NIC 0 を外す・制限する機能ができたら再検討する）。

## 3. 方法

使い捨ての Alpine の VZ の VM（`hanalima-e2e-iso`）を作り、ゲストの中から各経路に接続を試した。Mac 側には、`127.0.0.1` だけで待ち受ける一時的な HTTP サーバー（ポート 18765）を立てた（LAN には公開しない）。ゲストのポートの転送は、ゲストで `0.0.0.0:18766` を待ち受け、Mac の `127.0.0.1:18766` に届くかで調べた。終了後に VM とサーバーを片付けた。

設定は 3 段階で試した:

1. 既定
2. 共有なし（`mounts: []`）、すべてのポート転送を無効（`portForwards: [{guestIP: 0.0.0.0, guestIPMustBeZero: false, guestPortRange: [1, 65535], proto: any, ignore: true}]`）、`hostResolver.enabled: false`
3. 2 に加えて `plain: true`

## 4. 結果

| 経路 | 既定 | 2 | 3（`plain`） |
|---|---|---|---|
| ホームの共有 | 開 | 閉 | 閉 |
| ゲストのポートを Mac の `127.0.0.1` へ自動転送 | 開 | 閉 | 閉 |
| ゲストエージェント（vsock で Mac 側の hostagent へ） | 動く | 動く | 起動しない |
| インターネット（`1.1.1.1:443`、名前解決） | 開 | 開 | 開 |
| DNS | 開 | 開（`192.168.5.2` で引ける） | 開 |
| LAN のルーター | 開 | 開 | 開 |
| Mac の `127.0.0.1` だけで待ち受けるサービス（`192.168.5.2`、`host.lima.internal`） | 開 | 開 | 開 |
| Mac の LAN 側の IP | 閉 | 閉 | 閉 |

- ゲストのインターフェースは、どの設定でも `eth0`（192.168.5.15/24、ゲートウェイ 192.168.5.2）だった。hostagent のログでは、NIC 0 は usernet（gvisor）で提供されている。
- `hostResolver.enabled: false` にしても、ゲストの `nameserver` は 192.168.5.2 のままで、名前解決もできた。
- `ls /Users` が成功したのは、最初の起動で作られた空のマウントポイントが残っているだけで、マウントは 0 件だった。

## 5. HanaLima への影響

- 作成画面の「ホームフォルダを共有」をオフにしても、閉じられるのは**ファイル**だけで、ネットワーク経由では Mac の `127.0.0.1` のサービスに届く。作成画面の説明、README、サイトにその旨を書いた（2026-10-14）。
- AI のエージェントなどを動かす VM では、Mac で `127.0.0.1` に開いている開発用のサーバーやデータベースも、VM から操作されうると考えておく。
- 本格的な隔離が必要なら、Lima とは別の、ホストとの連携を持たない環境を使う。

## 6. 追記（2026-11-05）: Lima を改造せずに NIC 0 を切る 2 つの道

- **QEMU の VM なら今すぐできる**: Lima は `QEMU_SYSTEM_AARCH64` で QEMU の実行ファイルを差し替えられるので、引数の `-netdev user,...` に `restrict=on` を足すラッパーを挟めば、SLIRP がゲスト発の通信をすべて落とす（`hostfwd` の SSH は残るので `limactl shell` は使える）。制御はホスト側なのでゲストの root にも解除できない。VZ には相当する設定がない。再起動のたびにラッパーの指定が要る。HanaLima が QEMU の VM に「隔離」の切り替えとして実装する余地がある（未実装・未検証。ChatGPT との検討ログより）。
- **VZ は外部ドライバーで**: NIC 0（usernet）は vz ドライバーの中で作られるので、HanaLima のドライバーに替えれば付けない選択ができる。SSH とゲストエージェントは vsock で届く。詳細は [docs/09](09-external-driver-investigation.md) の「隔離への応用」。

## 7. 追記（2026-11-05）: HanaLima のドライバーで NIC 0 を外した

§6 の「VZ は外部ドライバーで」を実装した（docs/09 段階 4）。`vmType: hanalima` の VM で `vmOpts.hanalima.usernet: false` にすると、ドライバーは usernet を起動せず、NIC 0 はどこにもつながない状態で付ける（cidata が eth0 を期待するため。無いと cloud-init がネットワーク設定を捨てて毎回 2 分待つ）。SSH・ゲストエージェント・ポート転送は vsock を通る（systemd 256 以降の `systemd-ssh-generator`。Ubuntu 24.10 以降、Fedora 41 以降。Alpine は不可）。

実測（Ubuntu 26.04、E2E `DriverIsolationEndToEndTests`）: NIC なしでは `lo` だけで、経路なし、DNS なし、インターネット・192.168.5.2（Mac の 127.0.0.1 への入口）に届かない。HanaLima のホストオンリー NIC を足すと、そのサブネットのゲートウェイ（Mac）には届き、インターネットには届かない。§2 の結論のうち「Lima を改造せずに Mac から切り離すことはできない」は、Lima の外部ドライバーの仕組みを使えば（Lima 自体は無改造のまま）成り立たなくなった。残る接点は、共有フォルダ（作成時に外せる）、vsock（SSH とゲストエージェント。Lima の運用に必要）、そして HanaLima のネットワークを足した場合の、そのサブネット上の Mac（`0.0.0.0` で待つサービスには届く）。
