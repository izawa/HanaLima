# 19. Mac に挿した USB 機器を VM に渡せるか（2026-11-25 調査）

Mac に挿した USB メモリを、ファイルの共有ではなく**機器として** VM に渡せるかを調べた。ゲストの xHCI のバスに機器が現れ、ゲストのドライバーが `/dev/sdX` を作る形である。macOS 27.2.1、Xcode 27 の SDK、Lima 2.3.0、ゲストは Ubuntu 26.04（kernel 7.0）で確かめた。試作はブランチ `spike/usb-passthrough`（`Driver/` の `USBPassthrough.swift` と hosted モードの `--usb-passthrough`、`Prototypes/usb-passthrough-spike/`）にある。

## 結論

- **できる。** macOS 27 の Virtualization.framework に `VZUSBPassthroughDevice` が入り、Mac に挿さった USB 機器を VM が占有して使える。機器は同じく macOS 27 の AccessoryAccess（`AAUSBAccessoryManager`、`AAUSBAccessory`）で受け取る。
- **対象は HanaLima のドライバーの VM だけ。** VM を自分のプロセスで動かしているのが HanaLima のドライバーだけだからである。Lima の vz と QEMU の VM には付けられない。
- **どの機器を渡すかは、利用者がメニューバーで決める。** 機器ごとに「仮想マシンアクセサリ」のメニューで「“＜アプリ＞” で使用」か「“このMac” で使用」を選ぶ。アプリから割り当てる API は無い。
- **entitlement `com.apple.developer.accessory-access.usb` が要り、プロビジョニングプロファイルを埋め込んだアプリのバンドルでしか使えない。** ad hoc の署名と、バンドルの中に置いた素の実行ファイルでは、起動の時点で終了させられる。今の `Contents/Helpers/lima-driver-hanalima` のままでは使えない。
- **Lima が起動した、画面のないドライバーでも動いた。** ドライバーの実行ファイルを、プロファイルを持つバンドルの主実行ファイルにすれば、`limactl start` から起動しても機器を受け取って VM に付けられる。シンボリックリンク経由で起動しても同じだった。

## 仕組み

### API

- `VZUSBPassthroughDeviceConfiguration(device: AAUSBAccessory)` から `VZUSBPassthroughDevice` を作り、`VZUSBController.attach(device:)` で起動中の VM に付ける。`detach` で外す。どちらも VM のキューで呼ぶ。VM の構成には、起動の時点から `VZXHCIControllerConfiguration` が要る。
- 機器が抜かれると、`VZUSBController.Delegate` の `usbPassthroughDeviceDidDisconnect` が届き、VZ が自分で外す（macOS 27）。
- `AAUSBAccessoryManager.shared.registerListener(_:matchingCriteria:)` で、このアプリに割り当てられた機器の知らせ（`usbAccessoryDidConnect`／`usbAccessoryDidDisconnect`）を受ける。登録した時点で割り当て済みの機器は、完了の引数にも並ぶ。条件を空の配列にするとすべての機器が対象になる。条件を書いた絞り込みは、ほとんどの形で効かないと報告されている（FB24018643）。
- `AAUSBAccessory` は NSSecureCoding に対応していて、XPC の表現（`createXPCRepresentation`）も作れる。

### 割り当て

機器を挿すと、メニューバーの「仮想マシンアクセサリ」に Mac の USB 機器が並ぶ。機器ごとに、受け取りを登録しているアプリと「このMac」から選べる。macOS は機器ごとに割り当て先を覚えている。割り当て先のアプリのプロセスが起動して受け取りを登録すると、その機器が届く。

割り当て先の名前は、VM の起動のしかたで変わる。HanaLima のアプリから起動した VM では「HanaLima で使用」と出た。ターミナルや launchd（ログイン時の自動起動の代わり）から起動した VM では「不明なアプリケーション」だった。ドライバーを入れ子のバンドル（名前「HanaLima Driver」）にしても変わらなかった。macOS はドライバーの起動元のプロセスを責任元にしていて、アプリから起動すれば HanaLima、そうでなければアプリのバンドルではない `limactl` になるためだと考えている。

Mac でマウントされている機器を割り当てると、責任元に「リムーバブルボリューム上のファイル」へのアクセスの許可が求められた（アプリから起動したときは「“HanaLima” から…」、launchd から起動したときは「“limactl” から…」）。許可するまで、機器はゲストの USB には出るが `/dev/sda` にならなかった。私の作業環境から起動したときは出なかった（責任元がすでに許可を持っていたため）。許可はシステム設定の「プライバシーとセキュリティ」→「ファイルとフォルダ」で取り消せる。

### entitlement とプロファイル

- 開発者のサイトでは「Claim USB Accessory」という capability で、App ID ごとに有効にする。Apple への申請は要らない（Xcode のポータルの定義でも `distributionApprovalRequired: false`）。配布の種類には Developer ID も含まれる。
- 2026-11-25 に App ID `FJYY683YHH.org.izawa.HanaLima` を作ってこの capability を有効にし、Developer ID のプロビジョニングプロファイル（期限 2044-11-20、Mac の限定なし）を作った。プロファイルはリポジトリの外の `~/Library/Developer/HanaLima/` に置いている。
- 署名には次の entitlement を並べる。前の 2 つはプロファイルと照合される。
  - `com.apple.application-identifier` = `FJYY683YHH.org.izawa.HanaLima`
  - `com.apple.developer.team-identifier` = `FJYY683YHH`
  - `com.apple.developer.accessory-access.usb`
  - `com.apple.security.virtualization`

## 実験

試作は、ドライバーの実行ファイルを、バンドル ID `org.izawa.HanaLima` のアプリのバンドル（`build/usb-spike/HanaLima USB Spike.app`）の主実行ファイルにしたものである。プロファイルを `Contents/embedded.provisionprofile` に置き、Developer ID で署名した（`Prototypes/usb-passthrough-spike/make-bundle.sh`）。ドライバーは、hosted モードの `--usb-passthrough` か、Lima のもとで VM のフォルダに目印のファイル `hanalima-usb-passthrough` があるときに、xHCI のコントローラーを付け、割り当てられた機器をすべて VM に付ける。ゲストは Ubuntu LTS（`hanalima-e2e-usb`、HanaLima のドライバー、シリアルに自動ログイン）。機器は 32 GB の USB メモリ（`8564:1000`）で、利用者の写真が入っていたので、ゲストからは読み取り専用のマウントと読み込みだけを行った。

## 設計（2026-11-25、Codex との対照設計）

実験の結果と制約を Codex に渡し、Claude の案は見せずに独立に設計させた。両案を突き合わせて、次のように決めた。比べた点は節の最後にまとめる。

### ドライバーの置き方と署名

- ドライバーを、アプリの中の入れ子のバンドル `HanaLima.app/Contents/Helpers/HanaLimaDriver.app` の主実行ファイル（`lima-driver-hanalima`）にする。バンドル ID は `org.izawa.HanaLima.driver` で、App ID とプロファイルを本体とは別に持つ。今の素の実行ファイルにはこの entitlement を付けられない（実験の E0）。アプリの `LIMA_DRIVERS_PATH` と hosted モードの起動は、入れ子のバンドルの `Contents/MacOS` を指す。
- 署名は、入れ子のバンドルを先に、外側のアプリを最後に行う。ドライバーの entitlement は、`com.apple.application-identifier`（`FJYY683YHH.org.izawa.HanaLima.driver`）、`com.apple.developer.team-identifier`、`com.apple.developer.accessory-access.usb`、`com.apple.security.virtualization` の 4 つ。外側のアプリは今の entitlement のまま。
- プロファイルはリポジトリの外に置き、`build-app.sh` に環境変数（`HANALIMA_DRIVER_PROFILE`）で渡して `HanaLimaDriver.app/Contents/embedded.provisionprofile` に写す。`release.sh` は、プロファイルが無い・期限切れ・App ID が合わないときに止まり、入れ子の署名と entitlement を確かめてから公証に進む。
- ad hoc の開発ビルドでは、ドライバーを virtualization だけで署名し、USB の機能は出さない。試すときは Developer ID とプロファイルで署名する。
- ターミナルの `limactl` 用に `DriverInstaller` が `<prefix>/lib/lima/` に置くものは、コピーではなく、アプリの中のドライバーへの絶対パスのシンボリックリンクにする。素のコピーは起動の時点で終了させられ、リンクなら動いた（実験の E1）。置き換えは、横に作ったリンクを rename で入れ替える。

### 受け取る VM

- HanaLima のドライバーの VM から、**受け取り先を 1 台だけ選ぶ**（「なし」か 1 台）。メニューバーで HanaLima に割り当てた機器は、すべてその VM に付く。システムが「機器ごとにアプリを選ぶ」形なので、HanaLima は「アプリから先の VM を 1 台選ぶ」だけにする。
- 選んだ VM は `~/Library/Application Support/HanaLima/` の小さな JSON に、VM のフォルダと `vz-identifier` で記録する。lima.yaml には書かない。`limactl clone` の複製や、同じ名前で作り直した VM は、識別子が違うので引き継がない。改名したら選び直す。
- ドライバーは起動のときにこの記録を読み、自分の VM と一致したときだけ受け取りを登録する。ほかの VM は今までどおり起動する。読むのは起動のときだけなので、選び直しはその VM の次の起動から効く。今の受け取り先が動いている間は、画面で選び直しを断る。
- 記録の読み書きは LimaKit に置き、アプリとドライバーで共有する。ドライバーはアプリが動いていなくても読むので、ログイン時の自動起動でも働く。

### VM の構成と流れ

- macOS 27 では、HanaLima のドライバーの VM すべてに xHCI のコントローラーを付ける。受け取り先かどうかは、受け取りの登録だけに効かせる。こうすると、選び直しで VZ の構成が変わらない。
- 休止の記録（`hanalima-state.json`）に xHCI の有無を書く。項目の無い古い記録は「無し」として、その構成で戻す。xHCI を付ける前に休止した VM も再開できるようにするためである。
- 受け取りは、VM を起動したあとと、休止から戻して再開したあとに登録する。どちらも `DriverCore.start()` の同じ場所で行う。条件は空の配列（すべての機器）。登録の時点で割り当て済みの機器と、後から届いた機器を、同じ処理で VM のキューに渡す。機器は registry ID で覚え、付けている途中のものも数える。
- 「このMac」に戻されたときや抜かれたときは、AccessoryAccess の切断と VZ の delegate の両方が届く。どちらが先でも同じ結果になるように片付ける。
- 一時停止の間は登録を保つ。止まっている間に届いた機器は、再開してから付ける。
- 停止・強制停止・休止を始めたら、新しく付けるのをやめる（実験では、止める途中に届いた機器を付けようとして VZErrorDomain 3 になった）。休止の保存に失敗して VM が動き続けるときは、受け取りを戻す。ドライバーが終われば、macOS が機器を Mac に戻す。
- 失敗しても VM は動き続ける。理由はドライバーのログと、制御ソケットの `status` に返す。`status` には、受け取り先かどうか、付いている機器の数、最後のエラーを足す。
- 試作のバイト列化の確かめは消す。

### 画面

- 受け取り先を選ぶ欄を 1 つ置く（「なし」と、HanaLima のドライバーの VM）。macOS 27 未満と、USB の entitlement の無いビルド（ad hoc）では出さない。
- 欄の横に、次の旨の説明を置く。「選んだ VM が動いている間に、メニューバーの仮想マシンアクセサリで機器を選ぶ。渡している間は Mac から使えない。Mac に戻す前に、ゲストでアンマウントする」。メニューに出る名前は「不明なアプリケーション」なので、説明にもそう書く。最初の割り当てで、Mac のリムーバブルボリュームへのアクセスの許可を求められることも書く。
- macOS 26 では AccessoryAccess を弱くリンクし、記録があっても無視して今までどおり起動する。

### 最初の一歩

画面を作る前に、製品と同じ置き方で試作を通す。2026-11-25 に、App ID `org.izawa.HanaLima.driver` に「Claim USB Accessory」を有効にして Developer ID のプロファイルを作り、`build/usb-spike/HanaLima.app` の入れ子のバンドルで確かめた（実験の表）。利用者の環境を変えないように、`/Applications` の HanaLima と `<prefix>/lib/lima/` のドライバーには触れず、`LIMA_DRIVERS_PATH` で試作を指した。ログイン時の自動起動は、`AbandonProcessGroup` を付けた launchd の仕事からの `limactl start` で代えた（付けずに仕事を外すと、配下の hostagent まで終わって VM が止まった）。

確かめていないこと: `/Applications` に入れた製品のビルドでの動き（公証を含む）、本物のログイン時の自動起動、HanaLima のアプリから起動した VM の責任元と許可のダイアログの名前、一時停止中の扱い。実装のあとに確かめる。

### 実装と確認（2026-11-25）

設計のとおりに実装した。主な場所は、受け取り先の記録とドライバーの entitlement の判定が `USBTarget`（LimaKit）、受け取りが `USBPassthrough`（ドライバー）、リンクを置くのが `DriverInstaller`、画面が概要タブの「USB 機器」の欄（`AppModel+USB`）である。署名は `build-app.sh`・`make-app.sh`・`release.sh`。試作の目印のファイルと hosted モードの `--usb-passthrough` は外した。

Codex のレビューを受けて、次を直した。受け取り先が動いている間はその VM 自身も切り替えられないようにした（外せてしまうと、ドライバーは受け取りを続けたまま別の VM を受け取り先にできた）。停止・休止の失敗に備えて、受け取りを「閉じる」のではなく「止めておく」形にした。一時停止からの再開のあとに付ける処理を、ドライバーの actor の中に移した。起動の途中で停止が始まったら受け取りを始めないようにした。`release.sh` で、プロファイルが USB の entitlement を許しているかも確かめるようにした。別の Lima のホームで動く受け取り先の扱いは、HanaLima が Lima のホームを 1 つしか扱わないので採らなかった。

Developer ID で署名した `build/HanaLima.app` のドライバーで、次を確かめた。

## 機器ごとに受け取る VM を分ける（2026-11-26 検討・実験・実装、未リリース）

v0.19.0 では、利用者がメニューで「HanaLima で使用」にした機器は、すべて受け取り先の 1 台に付く。これを、機器 A は VM_1、機器 B は VM_2 のように分けられるかを検討した。macOS が選ばせるのは機器ごとのアプリまでなので、HanaLima に届いた機器を HanaLima の中で VM へ振り分ける仕組みが要る。実装はブランチ `feature/usb-routing` にあり、リリースするかは決めていない。Codex にも独立に設計させ、両案を突き合わせた。

### 方式の候補

| 方式 | 仕組み | 分かっていること | 分かっていないこと |
|---|---|---|---|
| ドライバーごとに選ぶ（第一候補） | 動いているドライバーすべてが受け取りを登録し、共通の振り分け表と照らして自分の VM 宛ての機器だけを付ける | 1 台のドライバーが登録して受け取れる（v0.19）。アプリが動いていなくても働く | 2 つのドライバーが両方登録したとき、同じ機器の知らせが両方に届くか。上の実験はどれも登録したドライバーが 1 つだけだった。先に登録したほうにしか届かないなら成り立たない |
| アプリが配る（予備） | HanaLima 本体だけが受け取り、`createXPCRepresentation` の表現を宛先のドライバーへ送り、ドライバーが VM に付ける | ヘッダーには、XPC サービスへ渡すための表現であることと、機器を開けるのは「同じクライアントアプリの worker process」のうち 1 つに限ることが書かれている | 別の App ID で `limactl` から起動されたドライバーが、本体の worker と見なされるか。ログイン時の自動起動ではアプリがいない（設計の節でこの方式を採らなかった理由で、今も変わらない） |
| 専用の受け口が配る | 常駐する小さなプロセスが受け取り、上と同じく配る | — | 上の不明点に加え、常駐・署名・再接続の管理が増える。上の方式が通り、なおアプリのいないあいだも受け取る必要があるときだけ考える |

ヘッダーは、`AAUSBAccessoryManager` を Dock に出る通常のアプリから使うよう求めている。ドライバーは `.prohibited` のまま画面なしで登録しているので、これは v0.19 がすでに抱えるリスクで、ドライバーごとに選ぶ方式でも変わらない。消せるのはアプリが配る方式だけなので、方式を選ぶ決め手にはしない。

### 機器の見分け方

`registryID` は「このMac」との行き来のたびに変わる（実験の表）ので、規則には使わない。`deviceDescriptorData` から vendor と product は読めるが、シリアル番号は文字列の番号しか入っていない。文字列は IORegistry を `registryID` で引いて読む。開発機の `ioreg` では、カメラのシリアル番号が `SN0001`（同じ型で共通と思われる）、YubiKey にはシリアル番号が無かった。そこで規則は 2 種類にする。

- この機器: vendor・product・シリアル番号。
- このポートの機器: vendor・product・`locationID`。シリアル番号の無い機器用で、同じ型の 2 台を挿し替えると行き先も入れ替わる。

同じ規則に当たる機器が 2 台あれば、どちらも付けずに保留する。読んだのは Mac が使っている機器のプロパティで、HanaLima に割り当てて認識し直されたあとも同じ値が読めるかは確かめていない。

### 振り分け表とそのほかの扱い

- 表は `~/Library/Application Support/HanaLima/usb-routes.json` に置き、宛先は `USBTarget` と同じく VM のフォルダと `vz-identifier` で表す。lima.yaml に書かない理由は設計の節と同じで、複製が機器を取り合うからである。書くのはアプリ、読むのはドライバーで、形式と照合は LimaKit に置く。
- 表には、機器ごとの規則のほかに既定の行き先（default route）を 1 つ置く（2026-11-26 利用者と決めた）。既定の行き先は「なし」か HanaLima のドライバーの VM 1 台で、「なし」なら規則に当たらない機器はどこにも付けずに保留する。届いた機器は次の順に照らし、最初に当たった行き先に付ける。

  | 順 | 照らすもの | 行き先 |
  |---|---|---|
  | 1 | この機器（vendor・product・シリアル番号） | 指定した VM |
  | 2 | このポートの機器（vendor・product・`locationID`） | 指定した VM |
  | 3 | 既定の行き先 | 指定した VM か、なし（保留） |

  既定の行き先を置くのは、機器を 1 台の VM にしか渡さない人が規則を書かずに済み、例外の機器だけに規則を足せばよいからである。黙ってどこかの VM に付くおそれは小さい。HanaLima に届くのは、利用者がメニューで機器ごとに「HanaLima で使用」にしたものだけだからである。Codex の案は常に保留することだった。
- v0.19 の受け取り先 1 台は、規則が無く既定の行き先だけがある表として読み替え、別の仕組みとしては残さない。移行で利用者の使い方は変わらない。
- 行き先の VM が止まっているときは、その機器をどこにも付けず、行き先が起動したら付ける。ほかの VM に回すことはしない。受け取り手がいるあいだ macOS は機器を Mac に戻さない（下の「実験の結果」）ので、行き先が止まっていてほかの HanaLima の VM が動いていると、機器は Mac でも使えない。画面には「保留中（vm_1 の起動待ち）」のように出す。
- 両方の VM が動いているときに行き先を変えるには、検討の時点では「このMac」に一度戻してもらう形を考えていた。実験で、古いほうが付けるのをやめてから外せば、機器が新しい行き先へ約 1 秒で移ることが分かったので、規則を変えたら HanaLima がこの順で移す（下の「実験の結果」）。
- 複製と改名は、今と同じく規則を引き継がず、画面で選び直しを求める。
- 一時停止と休止は今の扱い（止めておく、待たせる、再開してから付ける）を使い、付けるかの判定に「自分宛てか」を足す。
- ドライバーの `status` は台数ではなく機器ごとの一覧を返し、画面では規則の行き先と実際に付いている先を分けて出す。

アプリから起動した VM と、ターミナルや自動起動で起動した VM とでは、メニューに出るアプリが「HanaLima」と「不明なアプリケーション」に分かれる。「HanaLima で使用」にした機器が後者のドライバーに届くかは分からず、届かなければ規則では直せない。制約として説明に書く。

画面は、すべての VM に共通の振り分けの画面を 1 つ置く。行は、機器、見分け方（シリアル番号の末尾かポート）、行き先（既定の行き先に従う・VM）、今の状態。VM ごとの切り替えにしないのは、同じ機器を 2 台でオンにできてしまうからである。概要タブの「USB 機器」の欄には、その VM が受け取っている機器と「振り分けを編集…」を置く。

### 決める前の実験

1. 2 つのドライバーが両方登録したとき、知らせが両方に届くか。テスト用の VM 2 台で、両方に登録させてどちらにも付けさせず、プロセスごとに登録完了時の一覧と接続の知らせを記録する。起動の順番も入れ替える。駄目なら、ドライバーごとに選ぶ方式はやめる。
2. 割り当てたあとの IORegistry から、シリアル番号と `locationID` が読めるか。1 と同時に記録できる。
3. アプリから起動した VM と、ターミナルや自動起動で起動した VM を混ぜたとき、機器がどう届くか。
4. 1 が駄目だったときだけ、アプリが配る方式で、Lima が起動したドライバーが XPC の表現を受け取って付けられるか。
5. 残った方式で、行き先の変え方（「このMac」を経る形と直接移す形）と、途中で抜いたときなどの復旧。

1 と 2 は試作のビルド 1 つと USB メモリ 1 本で確かめられる。

### 実験の結果（2026-11-26）

試作はブランチ `spike/usb-routing` にある。VM のフォルダに目印のファイル `hanalima-usb-observe` があると、ドライバーは受け取りを登録して、知らせと IORegistry の値をログ（`driver.stderr.log`）に書くだけにする。中身に `attach` とあれば、受け取った機器を VM に付ける。制御ソケットの `usbDetach` は、新しく付けるのをやめて、付いている機器を外す。製品と同じ置き方のドライバーを Developer ID で署名し、`LIMA_DRIVERS_PATH` で指して、テスト用の VM 2 台（`hanalima-e2e-usb` は Ubuntu、`hanalima-e2e-usb2` は Alpine）をターミナルから起動した。機器は上と同じ USB メモリで、どの VM でも書き込みはしていない。

ドライバーが 2 つ動いていても、メニューに出た項目は「“不明なアプリケーション” で使用」の 1 つだけだった。macOS は 2 つのプロセスを 1 つのアプリとして扱っている。

| 試したこと | 結果 |
|---|---|
| 2 台が登録したあとで割り当てる（実験 1） | 2 つのドライバーに、同じ秒に同じ `registryID` の接続の知らせが届いた。「このMac」に戻すと、切断の知らせも両方に届いた |
| 割り当てたまま 2 台を止め、順番を入れ替えて起動し直す（実験 1） | 先に起動したほうは登録の時点で 0 台で、3 秒後に接続の知らせが届いた（受け取り手がいない間、機器は Mac に戻らず、最初の受け取り手が現れたところで認識し直された）。あとから起動したほうは、登録の完了の引数に同じ機器が入っていた |
| 割り当てたあとの IORegistry（実験 2） | 機器を開けずに、`registryID` から `IOUSBHostDevice` が引け、製品名、製造元、シリアル番号、`locationID`、パスが読めた。2 つのドライバーで同じ値だった |
| 割り当てを繰り返し、別のポートに挿し替える（実験 2） | `registryID` は割り当てのたびに変わった。シリアル番号は変わらなかった。`locationID` は同じポートなら変わらず（52511744）、別のポートでは変わった（51466240。その前にそのポートに挿していた HD-LE-B と同じ値で、挿した場所で決まる） |
| 片方だけが付ける | 付けたほうのゲストに `sda` が出た。付けなかったほうには何も届かなかった |
| 付けた VM を止める | 機器は Mac に戻らず、認識し直されて、まだ登録しているもう 1 台に接続の知らせが届いた。そのドライバーを付ける設定で起動し直すと、付けられた |
| 2 台とも付ける設定で、ほかの VM に付いている機器を付けようとする | 約 5 秒で VZErrorDomain 30003（「Device initialization failure」）になった。両方に付くことはない |
| 付けている VM に `usbDetach`（動いたまま外す） | 外す処理はすぐ済み、2 台に切断の知らせ、約 1 秒後に認識し直された機器の接続の知らせが届いた。付けるのをやめていたほうは何もせず、もう 1 台が付けた。ゲストで確かめると、機器は移った先にだけあった |
| すべてのドライバーが終わる | 機器は Mac に戻ってマウントされた |

知らせの届き方と付け外しについては、これでドライバーごとに選ぶ方式に要ることがそろった。知らせはすべてのドライバーに届き、付けるのは 1 つだけで、ほかには影響しない。動いたまま行き先を移すこともできる。ただし、実装したあとの確認で、ドライバーが終わるときに macOS のデーモンが落ちる問題が見つかった（下の「実装の確認」）。実装では次の 3 点を守る。

- 外す側は、付けるのをやめてから外す。順序が逆だと、認識し直された機器を自分でまた付ける。
- 取り合いは起こさない。ほかの VM に付いている機器を付けると、失敗するまで約 5 秒かかり、エラーの文面も「使用中」ではない。振り分け表で行き先を 1 つに決め、ドライバーは自分宛ての機器だけを付ける。
- 規則には `registryID` を使わず、シリアル番号か `locationID` を使う。

確かめていないこと: アプリから起動した VM と、ターミナルや自動起動で起動した VM を混ぜたとき（実験 3）。今回はすべてターミナルから起動した。アプリが配る方式の実験（4）は要らなくなった。

### 実装の設計（2026-11-26、Codex との対照設計）

上の方針を実装に落とした設計である。Claude と Codex が独立に書き、突き合わせて決めた。比べた点は節の最後にまとめる。

**振り分け表。** `usb-routes.json` は次の形にする。

```json
{
  "version": 1,
  "revision": "694DEF20-1C45-48B1-8A42-83E0097E17D2",
  "defaultRoute": null,
  "rules": [
    { "match": { "vendor": 34148, "product": 4096, "serial": "13AS0M7DAIL51OXI" },
      "destination": { "instanceDir": "/Users/<ユーザー>/.lima/vm1", "machineIdentifier": "…" } },
    { "match": { "vendor": 1041, "product": 808, "locationID": 51466240 },
      "destination": { "instanceDir": "/Users/<ユーザー>/.lima/vm2", "machineIdentifier": "…" } }
  ]
}
```

- `defaultRoute` は `null`（なし、保留）か、宛先と同じ形の VM。宛先は `USBTarget` の値と照合をそのまま使う。規則の `match` は `serial` か `locationID` のどちらか 1 つを持つ。同じ `match` の規則が 2 つある表は、保存のときも読むときもエラーにする。「既定の行き先に従う」は規則を消す操作になる。
- `revision` は保存のたびに新しい UUID にする。ドライバーが読んだ版を `status` で返し、アプリはそれで反映を確かめる。
- 書くのはアプリだけで、表全体を確かめてから atomic に置き換える。改名・複製・作り直しで照合できなくなった規則も消さずに残し、画面で選び直しを求める。
- 移行: `usb-routes.json` が無く `usb-target.json` があれば、その受け取り先を `defaultRoute` とする表として読む。この読み替えは LimaKit の 1 か所に置くので、更新のあとアプリより先に自動起動した VM も今までどおり受け取る。アプリは新しい表を保存してから古いファイルを消す。
- 表が読めない・壊れている・知らない版のときは、古いファイルに戻らない。ドライバーは新しく付けるのも規則による取り外しも止め、付いている機器はそのままにして、エラーを `status` で返す。アプリも知らない版を上書きしない。
- v0.19 のドライバーが動いているあいだ（`status` に振り分けの欄が無く `usbTarget` が真）は、行き先を変える編集を止め、その VM の再起動が要ると出す。古いドライバーは新しい表を読まないので、機器を取り合うおそれがあるからである。

**変更の伝え方。** ドライバーは表を置いたフォルダ（`~/Library/Application Support/HanaLima/`）を監視し、変わったら読み直す。ファイルそのものを監視すると、atomic な置き換えのあと古い inode を見続けるので、フォルダを監視する。同じ `revision` なら何もしない。監視を始めてから最初に読む。起動と休止からの再開のあと、付ける直前にも読む。アプリが保存の途中で終了しても伝え漏れが残らないので、制御ソケットに読み直しの命令は足さない。

**照合。** 機器を受け取るたびに、`registryID` から IORegistry の `IOUSBHostDevice` を引き、vendor・product・シリアル番号（`USB Serial Number`）・`locationID`・製品名・製造元を読む（試作の `USBObserver` と同じ）。シリアル番号は文字列のまま比べる。

| 状態 | 行き先 |
|---|---|
| シリアル番号の規則に 1 台だけ当たる | その規則の VM |
| シリアル番号の規則が無く、ポートの規則に当たる | その規則の VM |
| どの規則にも当たらない | 既定の行き先（`null` なら保留） |
| 同じ規則に 2 台以上が当たる | 当たった機器をすべて保留（識別情報が重複）。ほかの規則や既定の行き先には回さない |
| IORegistry が読めず、当たる規則を決められない | 保留（識別情報を取得できません）。次の接続の知らせで読み直す |
| 行き先の VM が止まっている・休止中 | 保留。ほかの VM には回さない |

「シリアル番号が無い」は読めた結果で、「読めなかった」と区別する。vendor と product の組に規則が 1 つも無ければ、IORegistry が読めなくても既定の行き先に付ける。重複は、そのドライバーが知っている接続中の機器すべてで判定する。2 台目が後から現れたら、先に付けた 1 台も外す。画面では、重複したシリアル番号の規則を、それぞれのポートの規則に一度に直せるようにする。

**ドライバー。** macOS 27 で、entitlement があり、xHCI の付いた HanaLima のドライバーの VM は、すべて起動と再開のあとで受け取りを登録する（v0.19 の受け取り先の判定はやめる）。`USBPassthrough` は、知らせを受けた機器を `registryID` ごとに 1 つの記録（アクセサリ、識別情報、判定した行き先、状態、操作のトークン、付けていれば VZ の device）で持つ。自分宛てでない機器も一覧に残す。知らせ・表の変更・再開・VZ の完了は VM のキューに集めて、同じ照合の処理を呼ぶ。

行き先を A から B に移すときの順序:

1. A は新しい表を読んだら、その機器を新しく付けるのをやめてから `detach` する。ほかの機器はそのまま使い続ける。付けている途中の機器は、完了を待って記録してから外す。
2. 外れた機器は認識し直され、新しい `registryID` で全ドライバーに届く。A は新しい表で自分宛てでないので何もしない。B は自分宛てなので付ける。
3. B が新しい表を読んだ時点で、すでに知っている機器が新しく自分宛てになった場合は、すぐには付けずに 2 秒待つ。A が使っていれば、そのあいだに外れて古い `registryID` が消え、2 の知らせで付けることになる。誰も使っていなかった（保留だった）機器なら、2 秒後にまだあれば付ける。A の取り外しが 2 秒より遅れると、30003 で 1 回空振りする（約 5 秒）が、2 の知らせで付くので結果は変わらない。

Codex は、機器ごとのロックファイル（`flock`）で VZ を操作するドライバーを 1 つに限る案だった。順序は確実になるが、`registryID` が接続のたびに変わるのでロックファイルが増え続けること、異常終了や消えたファイルの扱いが要ることから、採らなかった（2026-11-26 利用者と決めた）。失敗した B の試みが、A が使っている最中の機器に悪い影響を与えないかは、実機の E2E で確かめる。

一時停止・停止・休止は今の扱いを保つ。一時停止中は付いている機器を保ち、表の変更による取り外しも付け直しも再開まで延ばす（一時停止中の `detach` が効くとは仮定しない）。停止・強制停止・休止を始めたら全体を止め、表が変わっても再開しない。失敗して VM が動き続けるときは、最新の表で照合し直す。

**`status`。** `DriverControl.Response` に `usbRouting` を足す。中身は、受け取りの状態（準備中・受け取り中・登録失敗）、読んだ `revision`、表の読み込みのエラー、`devices`（`registryID` を 16 進の文字列で、vendor・product・製品名・シリアル番号・`locationID`、当たった規則の種類、判定した行き先か保留の理由、状態（付けた・付けている途中・外している途中・待っている・失敗）、最後のエラー）。古いドライバーの応答も読めるように、欄はすべて省略できる形にする。

**アプリ。** サイドバーに「USB 機器」を置く（ディスク・ネットワークと並べる。今の表示条件と同じく、macOS 27 と USB の entitlement のあるビルドだけ）。

- 上に「既定の受け取り先」（なし（保留）と、HanaLima のドライバーの VM）。
- 機器の一覧は、動いているドライバーそれぞれの `status` の `devices` を `registryID` で合わせたもの。アプリ自身は受け取りを登録せず、Mac の USB 機器を列挙もしない。列は、機器（製品名、シリアル番号の末尾かポート）、受け取り先（既定に従う・VM）、今の状態。
- 状態の例: 「vm1 で使用中」「vm1 から取り外し中 → vm2」「保留中（vm2 の起動待ち）」「保留中（既定の受け取り先なし）」「保留中（識別情報が重複）」「設定を反映中」（ドライバーの `revision` が古い）「状態を確認できません」（応答が無い）。応答が無いことを「保留」や「0 台」と読み替えない。
- 保留の説明として「HanaLima に割り当てられています。Mac で使うには、メニューバーで「このMac」を選んでください」と出す。使用中のストレージの行き先を変えるときは、保存の前に「元の VM でアンマウントしてください」と出す。
- 今つながっていない機器の規則も一覧に残し、編集と削除ができる。
- 概要タブの「USB 機器」の欄は、その VM が実際に受け取っている機器と「振り分けを編集…」だけにする。v0.19 の「受け取り先が動いている間は変えられません」は外す（動いたまま移せるため）。

**最初の版で外すもの。** ロックファイルによる排他、アプリの受け取りと XPC での受け渡し、常駐の受け口、Mac の USB 機器の列挙、ワイルドカードの規則、規則の手での優先順位、ゲストでの自動のアンマウント、VM の自動起動、試作の目印のファイルと `usbDetach`。

### 実装の確認（2026-11-26）

上の設計のとおりに実装した（ブランチ `feature/usb-routing`、main には入れていない）。Developer ID で署名したビルドで、テスト用の VM 2 台（`hanalima-e2e-usb` は Ubuntu、`hanalima-e2e-usb2` は Alpine）を使って確かめた。振り分け表はファイルを直接書き換えて変えた。画面からの操作はまだ確かめていない。

| 確かめたこと | 結果 |
|---|---|
| USB メモリはシリアル番号の規則で Ubuntu へ、規則の無い機器は既定の受け取り先の Alpine へ | USB メモリは Ubuntu に、外付けの HDD（HD-LE-B）は Alpine に、同時に付いた。どちらのゲストにも `sda` が出た（マウントはしていない） |
| 両方の VM を動かしたまま、USB メモリの規則の受け取り先を書き換える | 古い受け取り先が外し、約 1 秒後に新しい受け取り先が付けた。2 往復させ、30003 の空振りは起きなかった |
| 既定の受け取り先を「なし」にする | HD-LE-B が Alpine から外れ、両方のドライバーで保留になった。Alpine に戻すと、2 秒待ってから付いた |
| 受け取り先の VM を止める | その VM 宛ての機器は、もう 1 台には付かずに保留になった |

**VM に渡せない機器がある。** Apple の SD カードリーダー（05ac:8409）は「This device is not currently supported.」、USB のカメラ（0c45:6366）は「A USB passthrough device with isochronous endpoints is not supported.」で、どちらも VZErrorDomain -6 だった。映像や音声を isochronous 転送で流す機器（カメラ、オーディオインターフェース）は渡せないと考えられる。ドライバーは、この 2 つのエラーのあとは同じ機器を付け直さない。

**ドライバーが終わるときに、`accessoryaccessd` が落ちることがある。** 機器を付けたドライバーの VM を止めた直後に、macOS の `accessoryaccessd`（root で動く AccessoryAccess のデーモン）が SIGSEGV で落ちて起動し直した。クラッシュレポート（`/Library/Logs/DiagnosticReports/accessoryaccessd-*.ips`）は 4 つで、どれも同じ場所（XPC の接続のイベントの処理の中、NULL の参照）だった。1 つは 2026-11-25 19:09 で、v0.19 の形（受け取りを登録するドライバーは 1 つ）で USB メモリを付けた VM を止めたときだった。デーモンが落ちると、次のことが起きた。

- 動き続けているほかのドライバーに、すべての機器の切断の知らせが届き、その後は知らせが届かない。ゲストには機器が付いたまま残る。
- メニューのエージェント（Virtual Machine Accessories、`com.apple.accessoryaccess.uiagent`）が古いデーモンを相手にしたままになり、割り当てを変えられない、機器が一覧から消える、といった食い違いが出る。`killall "Virtual Machine Accessories"` のあと `launchctl kickstart gui/<uid>/com.apple.accessoryaccess.uiagent` で起動し直すと戻った（動いている最中の `kickstart -k` は SIP が許さない）。
- デーモンが起動し直したあと、割り当てがすべて「このMac」に戻ったことと、戻らなかったことがあった。

ドライバーは VM が止まると受け取りの登録を外す（`unregisterListener`）が、その完了を待たずにプロセスを終えていた。完了を最長 2 秒待ってから終わるようにすると、落ちなくなった。待つ処理は、ドライバーの actor の外で行う（待つあいだも `status` に答えるため）。

| ドライバー | 機器を付けたまま止めた回数 | デーモンが落ちた回数 |
|---|---|---|
| 直す前（振り分けの実装） | 4 | 4 |
| 直したあと（振り分けの実装。1 台で 5 回、2 台で片方だけが付けて 3 回、2 台がそれぞれ付けて 3 回） | 11 | 0 |
| 直したあと（v0.19.1 の形。1 台で 5 回を 2 度） | 10 | 0 |

外す処理が 2 秒以内に終わらなかったことは一度もなかった。v0.19.0 も同じ終わり方をしていたので、この直しを v0.19.1 として配った。デーモンが落ちること自体は macOS の不具合なので、Apple に **FB25734514** として報告した（2026-11-26、sysdiagnose とクラッシュレポート 4 つを添付）。

直したあとでは、デーモンが落ちたときのドライバーの扱いも変えた。切断の知らせが届いても、VZ が付けたままの機器は記録から消さず、VZ が外したと知らせるまで残す。

**確認の途中で出た「予期しない取り出し」の通知。** 確認の途中で、Mac に戻っていた USB メモリに「予期しない取り出し」の通知が出た。VM を約 26 秒おきに止めては起動する確認を繰り返したので、Mac がマウントしている最中に VM がまた機器を取ったためと考えている。通知の時刻は分からなくなり、確かめられていない。

**画面からの操作（2026-11-26）。** USB メモリを 2 本（Transcend と I-O DATA）にして、アプリから起動した 2 台で、サイドバーの「USB 機器」から操作した。

| 操作 | 結果 |
|---|---|
| v0.19 の受け取り先（guest1）が残った状態で画面を開く | 既定の受け取り先として guest1 が出て、止まっているので 2 本とも「保留中（guest1 の起動待ち）」。最初の保存で `usb-routes.json` に置き換わり、`usb-target.json` は消えた |
| 保留中の機器に受け取り先を選ぶ | 確認なしで保存され、すぐにそれぞれの VM に付いた |
| 使用中の機器の受け取り先を変える | 「使用中の機器を外しますか？」が出て、「外して変更」で 1 秒かからずに移った |
| 規則の無い機器の受け取り先を「なし」にする | 規則のある機器には何も起きなかった |
| 使用中の機器を「規則の無い機器の受け取り先に従う」に戻す | 確認のあと外れて保留になり、どの VM にも Mac にも付かなかった |

**USB 3 の機器の `locationID` は経路で変わる。** Transcend は同じ穴に挿したまま、最初は `0x03114100`、VM のあいだで移したあとは `0x03214100` だった。前者は USB 2 の経路、後者は USB 3 の経路で、USB 3 の機器はどちらで認識されたかで値が変わる。「挿したポート」の規則は、このままでは USB 3 の機器で外れることがある。シリアル番号の規則には影響しない。経路の違いを無視して比べるか、規則に両方の値を持たせるかを、リリースの前に決める。

確かめていないこと: アプリから起動した VM と、ターミナルや自動起動で起動した VM を混ぜたとき（実験 3）、デーモンが起動し直したあとにドライバーが受け取りを登録し直せるか（いまのドライバーは登録し直さない。落ちる原因を直したので、当面は入れない）。画面の確認の片付けで 2 台を止めたとき、Alpine に付いていた I-O DATA の USB メモリ（NTFS）が Mac に戻らず、挿し直すまで IORegistry にも出なかった（保留で、どの VM にも付いていなかった Transcend は戻った）。前の確認では、付けていた機器は VM を止めると Mac に戻っていたので、止めた順番か機器の違いかを次に確かめる。
